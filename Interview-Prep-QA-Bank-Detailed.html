1. SOLID principles

So, the way I'd explain it is: S Single Responsibility basically means one reason to change per class. Example: split OrderController (HTTP) from OrderService (rules) from OrderRepository (persistence).

In practice, O Open/Closed basically means extend behavior without editing stable core code. Example: new PaymentProcessor implementations behind an interface instead of giant if/else in one class.

Now, L Liskov Substitution basically means subtypes must honor the contract of the base type. Example: a FakeClock used in tests must behave like a real clock for callers that depend on Clock.

The important part is that I Interface Segregation basically means small, focused interfaces so implementors are not forced to stub unused methods. Example: ReadableRepository vs WritableRepository instead of one fat CrudRepository for read-only clients.

One thing I'd also mention is that D Dependency Inversion basically means high-level modules depend on abstractions, not concrete infrastructure. Example: inject NotificationPort instead of constructing SmtpEmailClient inside a domain service.

2. What is ORM and how does it work?

So, the way I'd explain it is: an Object-Relational Mapper bridges object graphs in memory to relational tables. You declare entities (classes to tables, fields to columns, associations to foreign keys or join tables). At runtime the ORM translates your operations into SQL: persist/merge to INSERT or UPDATE, find to SELECT, lazy collections to extra SELECTs on access. Hibernate (JPA provider) tracks entities in a persistence context, computes a flush plan, and sends SQL to the JDBC driver on flush/commit. You gain productivity and portability; you pay in complexity (N+1, lazy loading surprises) and must still understand SQL.

3. SQL joins and types

So, the way I'd explain it is: INNER JOIN basically means only rows that match on both sides. LEFT OUTER: all rows from the left; NULLs where no match on the right. RIGHT OUTER: mirror of LEFT (less common). FULL OUTER: all rows from both sides with NULLs where missing. CROSS JOIN: Cartesian product (every left row every right row). SELF JOIN: a table joined to itself (aliases) for hierarchies (e.g. employee to manager).

SELECT e.name, d.name AS dept
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;

SELECT c.name, o.id AS order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;

4. Database locks optimistic vs pessimistic

So, the way I'd explain it is: Pessimistic basically means lock rows before you change them (e.g. SELECT ... FOR UPDATE). Others block or fail until the lock releases. Good when contention is high and conflicts are expensive.

In practice, Optimistic basically means no lock while reading; on write, check a version or timestamp. If another transaction changed the row, the update affects zero rows and you retry or fail. Good for read-heavy data with rare conflicts. In JPA: @Version for optimistic; LockModeType.PESSIMISTIC_WRITE for pessimistic.

5. Service A up, B down lost call and rollback

So, the way I'd explain it is: across services you usually do not rely on one global two-phase commit (2PC): it is brittle and not supported the same way on all databases or message buses. The usual patterns are:

One practical way I'd frame it is Saga basically means sequence of local transactions with compensating actions (undo steps) or forward recovery.

Another point I'd mention is Outbox + messaging basically means A commits business data and an outbox event in one DB transaction; a relay publishes to a broker; B consumes when available, so there is no lost intent if the broker is durable.

And a third thing I'd call out is Timeouts + idempotency basically means if the synchronous call to B fails, A can mark a pending state and retry or compensate.

One thing I'd also mention is that rollback A means either compensate (run an inverse operation on A's data) or avoid dual writes by making A's side effect last (event-driven). Pure REST + separate DBs without saga/outbox is where data gets inconsistent, so in an interview I'd name these patterns explicitly.

6. Cache and caching in-memory vs distributed, strategies

So, the way I'd explain it is: Cache basically means stores copies of data closer to consumers to cut latency and load. In-memory (per JVM: Caffeine, Guava, simple ConcurrentHashMap): fastest, not shared across instances. Distributed (Redis, Hazelcast): shared, survives restarts (depending on config), needs network.

In practice, Strategies basically means cache-aside (app reads cache, on miss loads DB and fills cache); read-through (cache loader pulls from source); write-through (writes go to cache and source together); write-behind (async write to source); refresh-ahead (proactive reload before TTL). Choose by consistency needs and write volume.

7. Redis vs in-memory cache pros/cons, implementations, shared-cache consistency

So, the way I'd explain it is: In-memory (e.g. Caffeine) basically means lowest latency, no extra infra; each instance can drift; invalidation must be broadcast if you need coherence across nodes.

In practice, Redis basically means shared source of truth for cached entries, pub/sub for invalidation, TTLs, clustering; network hop and operational cost.

Now, Spring Boot Caffeine:

@Bean
public CacheManager cacheManager() {
  CaffeineCacheManager mgr = new CaffeineCacheManager("users");
  mgr.setCaffeine(Caffeine.newBuilder().expireAfterWrite(10, TimeUnit.MINUTES));
  return mgr;
}

The important part is that Spring Boot Redis basically means add spring-boot-starter-data-redis and connection settings, then enable caching:

# application.yml
spring:
  data:
    redis:
      host: localhost
      port: 6379
  cache:
    type: redis
    redis:
      time-to-live: 600000  # ms

# Java
@SpringBootApplication
@EnableCaching
public class App {  }

One thing I'd also mention is that use @Cacheable("users") / @CacheEvict on service methods. Two microservices pointing at the same Redis instance share entries; for consistency use short TTLs, @CacheEvict or CacheManager.getCache("users").clear() on writes, or Redis pub/sub to broadcast invalidation after updates.

8. Reflection in Java

So, the way I'd explain it is: Reflection basically means inspects and invokes types at runtime: Class, Method, Field, constructors. The JVM exposes metadata the compiler normally hides. Uses: frameworks (Spring scans and injects beans, Jackson maps fields, Hibernate proxies), serialization, testing. Trade-offs: breaks encapsulation if abused, slower than direct calls, must handle checked exceptions. Example:

Method m = MyService.class.getMethod("hello", String.class);
Object out = m.invoke(instance, "world");

9. Deployment strategies rolling, blue-green, canary

So, the way I'd explain it is: Rolling basically means replace instances in waves; old and new versions coexist briefly; simple, no double capacity requirement.

In practice, Blue-green basically means two full environments; switch traffic from blue to green in one step; instant rollback by switching back; costs more capacity.

Now, Canary basically means send a small % of traffic to the new version; watch metrics/errors; ramp up or roll back. Reduces blast radius.

10. Profiling Spring Boot tools

So, the way I'd explain it is: Profiling basically means samples or instruments the JVM to find hot methods, allocations, and blocking. Monitoring tracks health and metrics over time. Spring Boot: spring-boot-starter-actuator exposes /health, /metrics; Micrometer exports to Prometheus, Azure Monitor, etc. Profiling tools: JDK Flight Recorder (JFR), VisualVM, Async Profiler, YourKit/JProfiler (commercial), and APM agents (Datadog, New Relic). Use profiling for CPU spikes; use metrics/traces for production baselines.

11. Application properties per environment and secrets

So, the way I'd explain it is: use application.yml plus profile-specific files: application-dev.yml, application-prod.yml, activated by spring.profiles.active. Order: defaults profile files env vars (highest for SPRING_DATASOURCE_URL style overrides). Secrets: never commit real passwords; use environment variables, Kubernetes secrets, Azure Key Vault, HashiCorp Vault, or Spring Cloud Config with encryption. Spring Boot 3.x supports structured config imports. Example skeleton:

# application-prod.yml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}

12. @Component, @Service, @Repository, @Controller

So, the way I'd explain it is: all are stereotype specializations of @Component for clarity and AOP/exception translation. @Service = business layer. @Repository = persistence; enables exception translation to Springs DataAccessException. @Controller = Spring MVC controller returning view names. Semantically identical for component-scan registration; conventions help readability and framework behavior.

13. @RestController vs @Controller

So, the way I'd explain it is: @RestController is @Controller + @ResponseBody on all handler methods return values serialize directly to HTTP body (JSON). @Controller is for classic MVC: return a view name resolved by a template engine unless you add @ResponseBody per method.

14. Dependency Injection in Spring Boot

So, the way I'd explain it is: springs IoC container constructs beans and injects dependencies. Constructor injection (preferred): immutable, test-friendly. Setter injection: optional/mutable dependencies. Field injection: @Autowired on fields works but harder to test and hides required dependencies. Spring resolves by type, then disambiguates with @Qualifier or @Primary.

@Service
public class OrderService {
  private final OrderRepository repo;
  public OrderService(OrderRepository repo) { this.repo = repo; }
}

15. Circular dependency

So, the way I'd explain it is: bean A needs B and B needs A. Constructor injection cycles fail at startup (neither can be created). Fixes: refactor to extract shared dependency C; use setter/field injection (not ideal); @Lazy on one side to break the cycle with a proxy; or invert design (events, facade). Best answer in interviews: fix the design; @Lazy is a last resort.

16. @Qualifier

So, the way I'd explain it is: when multiple beans implement the same type, @Qualifier("beanName") on a parameter or field selects which implementation to inject. Works with constructor injection.

public BillingService(@Qualifier("stripe") PaymentClient client) {  }

17. @Primary

So, the way I'd explain it is: marks one bean as the default when several candidates match the same type and no @Qualifier is present. Useful for a real implementation in production with test doubles as additional beans.

18. @Bean lifecycle, scopes, pattern

So, the way I'd explain it is: @Bean on a @Configuration method registers the return value as a bean (great for third-party classes). Default scope: singleton (one instance per container). Other scopes: prototype (new instance per injection), request/session/web socket in web apps. Lifecycle: instantiation dependency injection @PostConstruct / InitializingBean use @PreDestroy / DisposableBean on shutdown. Spring beans embody Dependency Injection and often Factory (the container as factory). Early destruction: for prototype beans Spring does not track full lifecycle; you manage cleanup yourself. Singleton beans live until the context closes unless you register a shutdown hook / custom scope.

19. @Controller replaced by @Service on a controller class

So, the way I'd explain it is: the class is still a bean, but Spring MVC does not treat it as a web controller (no @Controller/@RequestMapping handler mapping unless you add them manually and @Service would be misleading). Endpoints stop being registered; HTTP requests return 404 or fall through. Fix: restore @Controller or @RestController.

20. @Service replaced by @Controller on a service class

So, the way I'd explain it is: if you only swap the stereotype without HTTP mappings, behavior may be unchanged for injection, but the class is now labeled as a web layer component confusing. If you add request-mapping methods by mistake, business logic leaks into the web layer. Stereotypes dont change bytecode; conventions and team clarity suffer; some tooling/docs generators may misclassify the layer.

21. @PostConstruct and @PreDestroy

So, the way I'd explain it is: jakarta annotations for lifecycle hooks after dependency injection and before container shutdown. @PostConstruct void init() runs once after the bean is constructed and injected. @PreDestroy void cleanup() runs on graceful shutdown. Prefer them over XML init methods; for full control use Bean definitions with initMethod/destroyMethod.

22. Spring Security authentication & authorization flow

So, the way I'd explain it is: A chain of servlet filters runs per request. Filters establish/clear the SecurityContext, run authentication (form login, HTTP Basic, JWT filter, OAuth2 login), then authorization (URL access rules, method security). Successful authentication produces an Authentication object with authorities; authorization checks it against configured rules before reaching the controller.

23. Role-based access control (RBAC)

So, the way I'd explain it is: users have roles (e.g. ROLE_ADMIN); endpoints or methods require roles. Spring: store roles in UserDetails; enforce with hasRole('ADMIN') in SecurityFilterChain or @PreAuthorize("hasRole('ADMIN')"). Prefer method-level checks for fine-grained rules on top of coarse URL rules.

24. JWT with Spring Security

So, the way I'd explain it is: after credential validation, issue a signed JWT (claims: sub, roles, exp). Client sends Authorization: Bearer . Custom OncePerRequestFilter parses, verifies signature + expiry, builds UsernamePasswordAuthenticationToken, sets SecurityContextHolder. Stateless services scale horizontally; revocation needs denylist, short TTL, or refresh-token rotation.

25. OAuth2 / OIDC with Spring Security

So, the way I'd explain it is: typically authorization code flow with Spring Security OAuth2 Client: redirect to IdP, user signs in, callback with code, exchange code for tokens at the token endpoint. Resource servers validate access tokens (JWT introspection or signature). Full flow = authenticate user / delegate auth to IdP, obtain access token for APIs, validate tokens on resource server.

26. JWT vs OAuth tokens

So, the way I'd explain it is: JWT is a token format (signed JSON claims). OAuth 2 is an authorization framework; access tokens may be opaque or JWT. Comparing JWT vs OAuth mixes layers: OAuth often issues JWT access tokens. Opaque tokens require introspection; JWTs can be verified locally with the right keys.

27. Synchronous A and asynchronous B dependency injection

So, the way I'd explain it is: injection is the same: Spring injects both beans into constructors. @Async methods run on a task executor when called through the Spring proxy (self-invocation bypasses async). If B is async and A is sync, injecting B into A is fine; calling b.doWork() may return immediately while work runs on another thread design return types (CompletableFuture) and error handling accordingly. Circular dependencies still follow normal Spring rules.

28. Saga pattern in microservices (Spring Boot)

So, the way I'd explain it is: Choreography basically means services react to events (no central coordinator). Orchestration: a saga coordinator issues commands and tracks steps. Implement with: domain events + message broker (RabbitMQ/Kafka), idempotent consumers, compensating transactions, durable outbox. Spring projects: Spring Modulith events, or custom orchestrator service; Axon/LRA for heavier cases. Each local transaction commits; failures trigger compensating calls or retry policies.

29. Resilience4j

So, the way I'd explain it is: lightweight fault-tolerance library. Circuit breaker stops calling failing deps; retry with backoff; rate limiter; bulkhead isolates thread pools; time limiter. Spring Boot starter wires annotations or functional style around calls to other services.

@CircuitBreaker(name = "orders")
public OrderDto getOrder(String id) { return remoteClient.fetch(id); }

30. API Gateway

So, the way I'd explain it is: single entry for clients: routing to services, SSL termination, auth, rate limiting, request aggregation. Spring Cloud Gateway (reactive) or older Zuul. Features: predicates (paths/headers), filters (rewrite, add headers), load balancing (via service discovery), circuit breaking integration.

31. gRPC with Spring Boot

So, the way I'd explain it is: gRPC is HTTP/2 + Protobuf contracts, binary, fast, strongly typed. Spring: grpc-spring-boot-starter or community starters; define .proto, generate stubs, implement server stubs and channel-based clients. Features: streaming RPCs, interceptors, deadlines, metadata good for internal east-west traffic; browsers need gRPC-Web.

32. Circuit breaker and fault tolerance

So, the way I'd explain it is: A circuit breaker tracks failure rates; when thresholds exceed, it opens and fails fast (or calls fallback) instead of hammering a sick dependency. After a wait it half-opens to probe recovery. Fault tolerance combines timeouts, retries, bulkheads, and fallbacks so partial failures dont cascade.

33. Rate limiting in Spring Boot

So, the way I'd explain it is: protect APIs from abuse. Options: API Gateway filters (Redis + token bucket), Bucket4j library, Resilience4j rate limiter, or cloud WAF/CDN rules. Return 429 Too Many Requests with Retry-After. Distributed rate limits need shared storage (Redis).

34. Thread pool; heap vs pool vs stack

So, the way I'd explain it is: A thread pool reuses worker threads for tasks instead of spawning unbounded threads (e.g. ExecutorService with a fixed pool). Stack: per-thread call frames and local primitives/references fast, automatic. Heap: shared object storage across threads. Pool is not a third memory region like heap/stack; it is a managed set of threads (or connections in a connection pool). Dont conflate connection/thread pools with JVM memory areas.

35. Encapsulation without access modifiers

So, the way I'd explain it is: in Java, omitting modifiers means package-private still a modifier. Interview angle: encapsulation is hiding invariants behind methods; you can use package-private classes in the same package, or nested classes where outer controls construction. Java 9+ modules export only specific packages. Another angle: interface exposes operations; implementation class keeps fields private if the question forbids private, you rely on discipline and API design (unusual in production Java).

36. Constructor overloading compile-time or runtime polymorphism?

So, the way I'd explain it is: multiple constructors differ by parameter lists (overloading). The compiler picks the signature at compile time based on static types. That is not runtime (dynamic) polymorphism overriding instance methods is runtime polymorphism via virtual dispatch.

37. Hibernate: save, flush, commit

So, the way I'd explain it is: save/persist basically means associate entity with session (may generate ID). flush: synchronize persistence context to DB SQL may be sent but transaction not necessarily committed. commit: end transaction flush usually happens before commit, then DB commits. Without commit, another connection wont see durable changes. Flushing can occur automatically before queries that need a consistent view.

38. Abstract class vs interface; constructors

So, the way I'd explain it is: abstract class: can have state, concrete methods, constructors (called by subclasses). Cannot instantiate directly. Interface: traditionally abstract API; Java 8+ adds default/static methods. Abstract class may have constructors. Interfaces cannot have instance constructors; Java does not allow new Interface(). Interfaces may have private methods (Java 9+) as helpers inside defaults.

39. Inheritance vs composition

So, the way I'd explain it is: Inheritance basically means (is-a): subclass extends parent; tight coupling to parent implementation. Composition (has-a): class embeds collaborators behind an interface; easier to swap behavior. Modern guidance: prefer composition for flexibility; use inheritance for true taxonomies and framework templates.

40. Checked vs unchecked exceptions

So, the way I'd explain it is: Checked basically means extend Exception but not RuntimeException; compiler forces throws or try/catch signals expected recoverable conditions. Unchecked are RuntimeException/Error; optional handling often programming bugs or rare failures. Better depends: checked documents failures but clutters APIs; Spring favors unchecked data-access exceptions for ergonomics.

41. final keyword

So, the way I'd explain it is: final variable basically means assign-once (blank final set in constructor for fields). final method: cannot override in subclass. final class: cannot extend security/immutability (e.g. String).

42. Immutable class

So, the way I'd explain it is: state never changes after construction. Recipe: final class; all fields private final; no setters; defensive copies for mutable fields (collections, arrays); factory/static builder. Example pattern:

public final class Money {
  private final BigDecimal amount;
  private final String currency;
  public Money(BigDecimal amount, String currency) {
    this.amount = amount;
    this.currency = currency;
  }
  public Money add(Money other) {  return new Money(); }
}

43. Inheritance in microservices

So, the way I'd explain it is: services are independently deployable; you dont inherit a microservice. Code reuse uses shared libraries (careful with coupling), templates, or multi-module builds. Domain boundaries favor duplication of DTOs over tight shared domain models. Inheritance in OOP inside one service is normal; across services, prefer APIs and events.

44. Breaking a monolith into microservices

So, the way I'd explain it is: identify bounded contexts; extract non-core or high-churn domains first; define APIs and data ownership (no shared DB writes); add API gateway and auth; introduce async messaging for cross-context workflows; implement deployment, observability, CI/CD per service; strangle legacy by routing slices of traffic; plan data migration and dual-write periods carefully.

45. Loose coupling in microservices

So, the way I'd explain it is: services know little about each others internals: stable contracts (versioned APIs/schemas), asynchronous events to avoid synchronous chains, avoid shared databases, use discovery + gateway, tolerate independent release cycles. Tight coupling = shared tables, chatty synchronous calls, leaking entity models across boundaries.

46. OOP, access modifiers, constructors, loose coupling via inheritance

So, the way I'd explain it is: subtyping can reduce coupling to concrete classes if callers depend on interfaces/supertypes (polymorphism). But deep inheritance hierarchies increase coupling to parent implementations. Constructors chain with super(...); access modifiers hide fields so subclasses and clients go through controlled APIs that visibility discipline supports substitutability without exposing fragile internals.

47. Spring pooling & profiling

So, the way I'd explain it is: Pooling basically means HikariCP (default) pools JDBC connections reuse TCP/auth overhead. Task execution uses thread pools (TaskExecutionAutoConfiguration). Profiling: see Q10 use JFR, VisualVM, or APM to inspect CPU, threads, and JDBC stalls; correlate with pool metrics (active connections, threads).

48. Constructors in inheritance

So, the way I'd explain it is: constructors are not inherited and cannot be overridden you provide constructors in the child that call super(...). If the parent has only a private constructor, the child cannot subclass it unless the parent exposes a callable constructor (inner classes have special rules). Child cannot access parents private constructor from outside the parent class body.

49. Partitioning vs sharding

So, the way I'd explain it is: terms overlap colloquially. Partitioning often means dividing a table/index inside one DB instance for manageability/performance (e.g. SQL Server partitions). Sharding usually means horizontal partitioning across servers each shard holds a subset of rows with separate nodes; routing layer maps keys to shards. Sharding adds cross-shard query complexity and distributed transactions challenges.

50. gRPC vs REST

So, the way I'd explain it is: REST basically means over HTTP/JSON: human-readable, cache-friendly with HTTP semantics, universal browser/curl support. gRPC: binary Protobuf, contracts, streaming, strong typing, efficient better for internal service-to-service. REST is simpler for public APIs; gRPC needs tooling for browsers (gRPC-Web).

51. CAP theorem

So, the way I'd explain it is: in a distributed data store you cannot simultaneously guarantee Consistency (all nodes see the same data at the same time), Availability (every request gets a non-error response), and Partition tolerance (system works despite network splits) under partition, choose between CP (sacrifice availability) or AP (allow stale reads). Real systems pick tunable trade-offs (eventual consistency, quorum).

52. RabbitMQ with Spring Boot

So, the way I'd explain it is: message broker: producers publish to exchanges; bindings route to queues; consumers ack messages. Features: durable queues, persistent messages, DLX/DLQ, priority, TTL, RPC pattern with reply queues. Spring: spring-boot-starter-amqp, RabbitTemplate, @RabbitListener, Jackson message converters.

@RabbitListener(queues = "orders.q")
public void onMessage(OrderEvent evt) {  }

53. Horizontal vs vertical scaling

So, the way I'd explain it is: Vertical basically means bigger machine (more CPU/RAM). Simpler but hardware limits. Horizontal: more nodes + load balancing. Needed for high availability and elastic scale; requires stateless services, externalized session/cache, and data partitioning awareness.

54. String storage and string pool

So, the way I'd explain it is: String objects live on the heap. String pool (intern pool): literals and interned strings may be reused so identical literals share one instance. "a" == "a" can be true for literals; new String("a") creates a separate heap object unless interned. Immutability enables safe sharing.

55. == vs equals()

So, the way I'd explain it is: == compares reference equality (same object) for objects; for primitives, value equality. equals() is logical equality defined by the class (overridden in String, Integer, etc.). Example:

String a = new String("hi");
String b = new String("hi");
a == b        // false, different objects
a.equals(b)   // true, same characters

56. map vs flatMap on streams

So, the way I'd explain it is: map: one output per element (1:1). flatMap: each element produces a stream; those streams are concatenated (1:many flattened).

List<String> lines = List.of("a b", "c");
// map: Stream<String[]> or wrong shape  here use flatMap:
List<String> words = lines.stream()
    .flatMap(line -> Arrays.stream(line.split(" ")))
    .toList();
// map would give Stream<String[]> if you return split directly wrapped

57. Intermediate vs terminal operations

So, the way I'd explain it is: Intermediate basically means (lazy): return a new stream filter, map, sorted. Terminal: trigger processing and produce a result or side effect collect, forEach, reduce, count. Without a terminal op, the pipeline does nothing.

long n = list.stream().filter(x -> x > 0).count(); // count is terminal

58. Short-circuiting

So, the way I'd explain it is: some operations may finish without processing the entire stream: findFirst, anyMatch, allMatch (sometimes), limit. Important for infinite streams and performance.

boolean hasEven = numbers.stream().anyMatch(n -> n % 2 == 0);

59. What is a Stream? Interface or class?

So, the way I'd explain it is: A Stream<T> is a sequence supporting sequential/parallel aggregate operations. It is an interface in java.util.stream; factories like Collection.stream() return concrete internal implementations. Streams are not data storage they wrap a source and describe operations.

60. Functional interface

So, the way I'd explain it is: interface with exactly one abstract method (SAM); may have default/static methods. Enables lambdas. Examples: Runnable, Callable, Comparator, Predicate, Function. Annotation @FunctionalInterface documents intent and lets compiler enforce SAM.

@FunctionalInterface
public interface ScorePolicy {
  int score(String word);
}

61. TVFs in SQL

So, the way I'd explain it is: Table-Valued Functions basically means return a rowset you can use like a table in FROM/JOIN. SQL Server: CREATE FUNCTION RETURNS TABLE. Useful for parameterized views, reusable query logic. Dialect-specific syntax; contrast with scalar functions returning single values.

-- Illustrative (SQL Server style)
SELECT t.*
FROM dbo.MyTVF(@param) AS t;

62. Indexes types and performance

So, the way I'd explain it is: an index is a separate structure (commonly B-tree) mapping key values to row locators for fast lookup/sort/range scans. Clustered (SQL Server): table rows ordered like the index (one per table). Nonclustered: separate structure pointing to rows. Other variants: unique, covering, full-text. The optimizer chooses seeks/scans; good indexes reduce pages read; bad indexes hurt writes and storage. Evaluate with execution plans and statistics.

63. Hibernate Session, SessionFactory, caches

So, the way I'd explain it is: SessionFactory basically means heavy, thread-safe factory for Session objects; holds metadata and often connection pool. Session: unit-of-work scope; tracks managed entities (persistence context). First-level cache: automatic per-session identity map repeated get of same ID hits memory. Second-level cache: SessionFactory-scoped, optional (EHCache, Infinispan), for read-mostly entities. Query cache: caches result sets keyed by query + params sensitive to stale data; use carefully.

64. HashMap vs ConcurrentHashMap

So, the way I'd explain it is: HashMap basically means not thread-safe for concurrent writes; allows one null key. ConcurrentHashMap: concurrent reads/writes with segmented/CAS strategies (no single lock for whole map); no null keys/values; safer default for shared caches/registries.

65. HashMap internals

So, the way I'd explain it is: backed by an array of buckets. hashCode() is transformed (spread) to an index; keys in the same bucket are compared with equals(). Collision: multiple keys same bucket stored as linked list or tree (if many collisions). Load factor triggers resize/rehash. Correct equals/hashCode contract is mandatory.

66. ArrayList vs LinkedList

So, the way I'd explain it is: ArrayList basically means dynamic array; O(1) indexed access; amortized O(1) append at end; inserts in middle shift elements costly for large lists. LinkedList: doubly linked nodes; O(1) insert if iterator at position; poor cache locality; higher memory overhead per element. Default choice: ArrayList unless you frequently add/remove in the middle with list iterators or need a Deque API.
