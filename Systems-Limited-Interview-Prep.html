Java Streams — concepts

A Stream in Java is not a replacement for ArrayList. It is a lazy, possibly parallelizable pipeline for declaring what you want to do with a sequence of values without spelling out index loops everywhere. You start from a source (a collection, array, generator, or lines of a file). Then you chain intermediate operations such as filter, map, or sorted. Each intermediate returns another Stream and records a stage in the pipeline—but crucially, it does not process the whole dataset yet. Finally you run a terminal operation like collect, reduce, or findFirst. That terminal operation pulls data through the pipeline and produces a concrete result (a list, a count, an optional value, etc.). If you forget the terminal step, you have built a recipe you never executed.

The operation map applies a one-to-one function: every input element becomes exactly one output element, possibly of a different type. The operation flatMap is for the case where each input element could correspond to zero, one, or many outputs. You return a small stream per element, and flatMap concatenates those streams into a single flat stream. Without flatMap, you would end up with Stream<Stream<T>>, which is usually not what you want for business logic (though it appears in advanced patterns).

distinct relies on equals/hashCode for objects. sorted needs either natural ordering (Comparable) or a Comparator. peek is mainly for debugging side effects; in production code, avoid putting important logic in peek because readers assume it is observability only.

Short-circuiting operations can finish without seeing every element. For example, anyMatch stops at the first true predicate result; findFirst stops once it has a candidate; limit(n) stops after n elements have passed. That matters for infinite streams (like Stream.iterate) and for performance on large collections when the question is “is there any?” rather than “process all.”

Functional interfaces used by streams

Lambdas passed to stream operations must match a functional interface: an interface with a single abstract method. filter takes a Predicate<T> (T -> boolean). map takes a Function<T, R> (T -> R). forEach and peek take a Consumer<T> (accept a value, return void). Suppliers appear when streams generate values (Stream.generate) or provide seeds. Interviewers who ask “how does Stream use functional interfaces?” want you to name this mapping, not recite bytecode.

Streams — code & practice

The examples below are small, but each encodes a pattern you should recognize in interviews. When you read a pipeline, read it from source to terminal and ask: what is the type at each step, and does any step change cardinality (number of elements)? map preserves cardinality unless you map to null in older patterns (avoid nulls in streams—use Optional or flatMap). flatMap changes cardinality by design.

map vs flatMap

If each line of text is one stream element and you want one integer per line (its length), map is correct. If each line contains several words and you want a stream of words, each line must expand into multiple elements—so you split into an array or list, turn that into a stream, and use flatMap to merge those per-line streams into one continuous stream of tokens.

// map: Stream<String> -> Stream<Integer> (length each)
List<Integer> lengths = lines.stream().map(String::length).toList();

// flatMap: each line -> multiple tokens, one flat stream
List<String> tokens = lines.stream()
    .flatMap(line -> Arrays.stream(line.split("\\s+")))
    .toList();

grouping & counting

groupingBy is the stream equivalent of “build a map of buckets.” The classifier function decides the bucket key; the downstream collector decides what you store in each bucket (a list of items, a count, a sum, etc.). Collectors.counting() is a downstream collector that increments a long per bucket—perfect for word frequency or counting employees per department when you already have a stream of row-like objects.

Map<String, Long> freq = words.stream()
    .collect(Collectors.groupingBy(w -> w, Collectors.counting()));

int[] to List<Integer>

Primitive arrays are not the same as collections. To go from int[] to a list, the idiomatic bridge is an IntStream over the array, then boxed() to produce a stream of Integer, then collect(toList()). For huge arrays, consider whether you really need a List<Integer> or if an int[] / IntStream pipeline is enough.

List<Integer> list = IntStream.of(arr).boxed().collect(Collectors.toList());

Why Integer and not int in List<…>? In Java, generic type parameters must be reference types (classes or interfaces that extend Object). Primitives such as int, boolean, or double are not objects—they have no vtable, can live on the stack or inline in arrays, and cannot be used where the language expects an Object. So List<int> is a compile error; the collections API uses wrapper types (Integer, Boolean, Double, …) instead. The compiler inserts autoboxing and unboxing when you assign an int to an Integer or vice versa, but under the hood the list still stores Integer references. That costs extra memory and allocations compared to a plain int[], which is why hot numeric paths often stay primitive until the boundary where you truly need a collection API.

Practice 1 — sum of squares of evens

This pipeline filters to even numbers, maps each to its square, then reduces with a sum identity. reduce(0, Integer::sum) is clear; alternatively mapToInt + sum() avoids boxing in the middle. Interviewers sometimes ask “why not for-loop?”—answer: clarity and composability; also parallel streams for very large data (with caution).

int sum = ints.stream()
    .filter(n -> n % 2 == 0)
    .map(n -> n * n)
    .reduce(0, Integer::sum);

Practice 2 — flatten nested lists

If you have List<List<T>>, each inner list is one element of the outer stream. flatMap(List::stream) turns each inner list into a stream and concatenates. Method reference List::stream is equivalent to list -> list.stream(). The mental model is “one level of nesting removed.”

List<T> flat = nested.stream().flatMap(List::stream).toList();

Practice 3 — top N by salary

Sorting the entire employee list is simple but O(n log n). For huge data you might use a heap of size N (priority queue) instead—but for interviews, sorted(...).limit(n) is acceptable unless they ask scale. Note: sorted may buffer the whole stream if it is not explicitly ordered as incremental, so for parallel infinite sources this pattern is wrong; for a finite in-memory list it is fine.

List<Employee> top = employees.stream()
    .sorted(Comparator.comparing(Employee::getSalary).reversed())
    .limit(n)
    .toList();

Practice 4 — partition adults / minors

partitioningBy is a special case of groupingBy for predicates: it always produces exactly two buckets, true and false. It reads cleanly when your split is binary (adult/minor, active/inactive, paid/unpaid).

Map<Boolean, List<Person>> parts = people.stream()
    .collect(Collectors.partitioningBy(p -> p.getAge() >= 18));

Practice 5 — distinct by key (keep first)

There is no single “distinct by property” on Stream. A common idiom is collect to a map keyed by the property; the merge function (a, b) -> a keeps the first user encountered when duplicate emails appear. Then take values(). Order is only preserved if your stream had a meaningful order and the map implementation iterates accordingly—LinkedHashMap variants exist if you need stable order.

Collection<User> unique = users.stream()
    .collect(Collectors.toMap(User::getEmail, u -> u, (a, b) -> a))
    .values();

Practice 6 — teeing (two aggregates, one pass)

Collectors.teeing runs two collectors in one pass and merges their results. It is useful when you want both count and sum (or min and max) without traversing the stream twice. Java 12+ feature—mention version if asked.

var stats = numbers.stream().collect(Collectors.teeing(
    Collectors.counting(),
    Collectors.summingInt(Integer::intValue),
    (count, sum) -> Map.of("count", count, "sum", sum)));

Interview trick: Intermediate operations like map and flatMap return another Stream<R>; filter returns Stream<T> with the same element type. The final result type is entirely determined by the terminal operation: collect(toList()) gives a list, reduce might give an Optional or an integer, findFirst gives Optional<T>. Many wrong answers confuse “what map returns” with “what the whole expression returns.”

Optimization story (~40%) — STAR

Interviewers who ask “you said 40% improvement—how?” are testing whether you measured work or only refactored for aesthetics. STAR keeps you honest: Situation names the slow user journey (report, dashboard, nightly batch). Task states the goal in measurable terms (reduce p95 latency, cut CPU on SQL Server, shrink payload). Action is the technical meat: you identified N+1 queries with Hibernate statistics or logs, added covering indexes for the WHERE clauses your report used, introduced pagination on a grid that loaded thousands of rows, cached reference data that rarely changes, tuned Spring Batch chunk size and commit interval, or simplified a nested SQL anti-pattern. Result should be one number you actually saw—even a rough one—or you clarify that 40% was cumulative across several deployments.

If you cannot recall exact metrics, say what you would measure (APM traces, SQL execution plans, Micrometer timers) and what trend you observed qualitatively. Credibility beats exaggeration.

Answers: OOP & language rules

How did OOP make life easier?

Object-oriented programming lets you mirror the problem domain in code: a CareVisit, an Invoice, a User with roles. That mapping helps teams communicate and keeps related behavior near related data. Encapsulation means you can change how a class enforces rules without rewriting every caller. Polymorphism means frameworks like Spring can depend on interfaces (UserDetailsService, Repository) and swap implementations for tests or environments. Composition lets you assemble behaviors from smaller parts instead of growing fragile inheritance trees.

Abstraction vs encapsulation

Abstraction answers “what can I do with this object?” without exposing steps. A PaymentGateway interface with a charge() method is abstraction: callers do not care if Stripe or a mock is behind it. Encapsulation answers “how is state protected?” Private fields plus getters/setters (or richer methods) prevent other classes from putting an object into an invalid state—like a negative balance or a visit with no assigned carer.

// --- Abstraction: caller depends only on the contract ---
public interface PaymentGateway {
  void charge(long amountCents, String customerId);
}

public class StripeGateway implements PaymentGateway {
  public void charge(long amountCents, String customerId) { /* Stripe API */ }
}

public class MockGateway implements PaymentGateway {
  public void charge(long amountCents, String customerId) { /* no network */ }
}

public class CheckoutService {
  private final PaymentGateway gateway; // concrete type hidden
  public CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }
  public void pay(long cents, String id) { gateway.charge(cents, id); }
}

// --- Encapsulation: invariant enforced inside the type ---
public class CareVisit {
  private String carerId;
  private int durationMinutes;

  public void assignCarer(String id) {
    if (id == null || id.isBlank())
      throw new IllegalArgumentException("carer required");
    this.carerId = id;
  }
  public void setDurationMinutes(int m) {
    if (m <= 0) throw new IllegalArgumentException("duration must be positive");
    this.durationMinutes = m;
  }
}

Inheritance vs composition

Inheritance models an “is-a” relationship: a Manager is an Employee. It is powerful but dangerous when used for code reuse alone, because subclasses inherit parent internals and hierarchies become hard to refactor. Composition models “has-a” or “uses-a”: an OrderService has a PaymentClient and a InventoryClient. You can replace either dependency without rewriting the whole class tree. Modern guidance: favor composition for behavior reuse; use inheritance sparingly for true taxonomies.

// --- Inheritance: Manager *is an* Employee (shared state/behavior in base) ---
public abstract class Employee {
  protected final String id;
  protected Employee(String id) { this.id = id; }
  public abstract double monthlyPay();
}

public class Manager extends Employee {
  private final double baseSalary;
  public Manager(String id, double baseSalary) {
    super(id);
    this.baseSalary = baseSalary;
  }
  @Override public double monthlyPay() { return baseSalary + bonusForTeam(); }
  private double bonusForTeam() { /* ... */ return 0; }
}

// --- Composition: OrderService *has* collaborators (swap without subclassing) ---
public interface PaymentClient { void authorize(String orderId, long amount); }
public interface InventoryClient { boolean reserve(String sku, int qty); }

public class OrderService {
  private final PaymentClient payments;
  private final InventoryClient inventory;

  public OrderService(PaymentClient payments, InventoryClient inventory) {
    this.payments = payments;
    this.inventory = inventory;
  }

  public void placeOrder(String orderId, String sku, int qty, long amount) {
    if (!inventory.reserve(sku, qty)) throw new IllegalStateException("no stock");
    payments.authorize(orderId, amount); // body is NOT here — see classes below
  }
}

// Where authorize() is actually implemented: concrete types that implement PaymentClient
public class RestPaymentClient implements PaymentClient {
  public void authorize(String orderId, long amount) {
    // e.g. RestTemplate / WebClient POST to your payment microservice or Stripe API
  }
}

public class MockPaymentClient implements PaymentClient {
  public void authorize(String orderId, long amount) { /* unit tests: no HTTP */ }
}

At compile time, OrderService only knows the PaymentClient interface. The JVM dispatches authorize to whatever object was passed into the constructor—RestPaymentClient in production, MockPaymentClient in tests. In Spring Boot, you typically annotate one implementation with @Service (or declare a @Bean method); Spring injects it into OrderService because that class’s constructor asks for a PaymentClient.

Why Java does not allow multiple class inheritance

The diamond problem appears when class D inherits from B and C, and both inherit the same method from A—which implementation does D get? Languages with multiple inheritance need complex resolution rules. Java avoids that by limiting classes to one superclass, while allowing multiple interfaces. Java 8+ default methods on interfaces reintroduce some of the same design discipline: if two interfaces provide defaults, the compiler may force you to override explicitly.

// ---------- Does NOT compile: multiple class inheritance ----------
// class Dolphin extends Mammal, Fish { }
// error: '{' expected (Java only allows one class after extends)

// ---------- Works: one superclass + many interfaces ----------
abstract class BaseService { /* shared wiring */ }
interface Printable { void print(); }
interface Exportable { byte[] export(); }

class ReportService extends BaseService implements Printable, Exportable {
  public void print() { /* ... */ }
  public byte[] export() { /* ... */ }
}

// ---------- Works but needs your choice: two defaults, same signature ----------
interface Camera { default void snap() { System.out.println("click"); } }
interface Phone { default void snap() { System.out.println("screenshot"); } }

class Smartphone implements Camera, Phone {
  @Override
  public void snap() {
    Camera.super.snap();  // explicit call to one default
    Phone.super.snap();   // and/or the other — your merged behavior
  }
}

If Smartphone implemented Camera and Phone but did not override snap(), the compiler would error: two conflicting default methods. Writing @Override public void snap() fixes it; inside the override you may delegate with Camera.super.snap() / Phone.super.snap().

Parent and child references

A reference of type Parent can point to an object that is actually a Child at runtime. That is upcasting and is always safe. The reverse assignment from Parent variable to Child reference requires an explicit cast because the compiler cannot prove the runtime object is a child. If you are wrong, the JVM throws ClassCastException. A method that accepts Parent can be called with a Child instance because “child is a parent” in the type system—that is Liskov substitutability.

Parent p = new Child();   // OK
// Child c = new Parent(); // compile error
Child c = (Child) p;      // runtime OK only if p points to Child

Access modifiers and polymorphism time

Access control is about visibility boundaries: private (class only), package-private (no modifier, same package), protected (package plus subclasses—even in other packages), public (everywhere). Nested classes can see outer private members, which surprises people revisiting Java. Compile-time polymorphism is method overloading: the compiler picks the signature based on static types. Runtime polymorphism is overriding: the JVM resolves the implementation from the actual object’s class when you call an instance method through a superclass reference.

// ----- Access modifiers -----
public class Wallet {
  private int balance;       // only this class (not subclasses, not other classes)
  int lastFourDigits;        // package-private: same Java package only
  protected String ownerId;  // same package OR subclasses (even in other packages)
  public void deposit(int x) {
    if (x > 0) balance += x;
  }

  class Ledger {             // non-static nested class
    void adjust() {
      balance++;             // OK — nested class sees outer's private fields
    }
  }
}

// ----- Compile-time polymorphism = overloading (static binding) -----
class Printer {
  void print(int x) { /* int version */ }
  void print(String s) { /* String version */ }
}
// new Printer().print(42)   → compiler chooses print(int)
// new Printer().print("hi") → compiler chooses print(String)

// ----- Runtime polymorphism = overriding (dynamic dispatch) -----
class Animal {
  public void speak() { System.out.println("…"); }
}
class Dog extends Animal {
  @Override public void speak() { System.out.println("woof"); }
}
Animal a = new Dog();
a.speak();  // prints "woof" — JVM looks at real object (Dog), not type of reference (Animal)

Answers: JVM, GC, strings

Heap vs stack

Each thread gets its own stack made of frames. Each time a method is invoked, a frame is pushed with space for local variables and parameters (primitives and object references). When the method returns, the frame pops. The heap is shared memory where object instances live. References on the stack point to heap objects. Local primitives live entirely on the stack. This split matters for performance (stack allocation is cheap and automatic) and for thread safety: stacks are thread-local; heaps are shared and need synchronization if mutated concurrently.

Garbage collection and generations

Most modern JVMs use a generational heap. New objects are allocated in a young area (often Eden). A minor collection copies live objects to survivor spaces and discards garbage cheaply because most new objects die quickly. Objects that survive enough cycles are promoted to the old generation. Old-generation collections are more expensive and less frequent. GC determines reachability from GC roots (thread stacks, static fields, JNI roots). Anything not reachable is eligible for collection. You do not manually free memory in Java; finalizers are deprecated for good reason—never rely on them for cleanup; use try-with-resources.

How strings live in memory

String literals and some interned strings may live in a string pool so identical literals share one instance. That is why two variables assigned the same literal might compare true with == (reference equality). Using new String("text") forces a new heap object whose reference differs from the pooled literal unless you call intern(). In application code, always compare strings with equals unless you have a specific interning contract. Understanding this prevents subtle bugs and answers classic interview questions cleanly.

Literal vs new String

If a and b are both assigned the literal "java", they typically reference the same pooled instance, so a == b may be true. If c is new String("java"), it is usually a different object on the heap, so a == c is false even though the character content matches. a.equals(c) compares content and is true. Teach this as “== is identity, equals is value for strings.”

Streams vs collections storage

A Stream does not copy your collection into a new structure by default. It walks the source when a terminal operation runs (unless intermediate ops require buffering, like sorted on an unordered stream). So “where is stream stored?” is slightly the wrong question: the stream is a pipeline description; the backing data is still your list, array, or generator.

Calling System.gc()

System.gc() suggests garbage collection; the JVM may ignore it. Production services should not use it to “fix” memory issues—it causes pause surprises and hides real leaks. Fix references, pool sizes, and caches instead.

Answers: Java core

Abstract class vs interface

An abstract class can hold state (fields), constructors, and a mix of concrete and abstract methods. A class extends exactly one abstract class. An interface historically was pure contract; today it can have default and static methods with bodies. A class can implement multiple interfaces. Use abstract classes when subclasses truly share a common base implementation; use interfaces when many unrelated types should share behavior or when you need multiple types of contracts (common in Spring and testing with mocks).

Checked vs unchecked exceptions

Checked exceptions (subclasses of Exception but not RuntimeException) force the compiler to require throws declarations or try/catch. They were designed for recoverable conditions like I/O failures. Unchecked exceptions extend RuntimeException (including Error in a different branch you rarely catch). They signal programming errors or conditions you typically do not recover from in every caller—null pointers, illegal arguments. Modern APIs often prefer unchecked for brevity, but JDBC and many Java APIs still expose checked exceptions.

The final keyword

final on a variable means assignment once (for fields, must be set by constructor or initializer). On a method, it prevents overriding in subclasses—useful for security-sensitive or template methods. On a class, it prevents subclassing entirely (String is final). final also has subtle thread-safety semantics for correctly constructed immutable objects.

Immutability

An immutable object cannot change after construction. In Java this usually means all fields are final, no setters mutate state, and any mutable objects held (lists, dates) are not leaked or are defensively copied on get. String and Integer cache values are common examples. Immutability simplifies reasoning in concurrent programs because readers see a stable snapshot.

List vs Set

List is ordered (by index) and allows duplicates. Set enforces uniqueness per equals/hashCode for hash-based sets, or ordering rules for TreeSet. If you change equals without hashCode for elements in a HashSet, you break the set’s contract and get “impossible” bugs.

HashMap vs SortedMap / TreeMap

HashMap offers average constant-time lookup and insertion using hashing; iteration order is not meaningful. A TreeMap keeps keys sorted (natural order or comparator) with logarithmic cost per operation. Choose hash when you only need fast lookup; choose tree when you need sorted keys or range queries.

ArrayList vs LinkedList

ArrayList backs an array that grows; indexed access is O(1) and iteration is cache-friendly. LinkedList is doubly-linked nodes; “fast insert in middle” rarely matters in application code because you still have to walk to the node. In practice ArrayList is the default choice unless you have a deque-specific API need.

Array vs ArrayList

Arrays have fixed length and can hold primitives or references. ArrayList grows dynamically, stores references (boxed primitives), and integrates with generics. For large numeric workloads, primitive arrays avoid boxing overhead.

Functional interfaces and default methods

A functional interface has exactly one abstract method (counting methods inherited from Object as excluded). Lambdas and method references implement that interface silently at compile time. Default methods let Java add methods like stream() to Collection without breaking every implementing class—implementors inherit the default unless they override.

equals and hashCode contract

If two objects are equal via equals, they must return the same hashCode. The reverse is not required: unequal objects may collide on hash. If you break this, hash maps and sets malfunction. Always override both together for entity IDs or value objects. Use Objects.equals / Objects.hash to reduce boilerplate mistakes.

Answers: Streams Q&A

What is a Stream?

A Stream is an abstraction for processing sequences in a declarative way with optional parallelism. It emphasizes immutability of source (the underlying collection is not modified by stream ops unless you misuse forEach with side effects) and fluent pipelines. It is not serializable as a general data transport; it is a computation description.

Stream: interface or class?

java.util.stream.Stream<T> is an interface. The JDK provides internal implementations. Factory methods like collection.stream() construct concrete pipeline objects.

Intermediate vs terminal operations

Intermediate operations return a stream and are lazy—they build stages. Terminal operations trigger evaluation. Calling two terminals on the same stream usually fails (streams are one-shot); you must create a new stream from the source for another pass.

List<Integer> nums = List.of(1, 2, 3, 4, 5);

// filter + map are intermediate: they only describe the pipeline — no work yet
Stream<Integer> pipeline = nums.stream()
    .filter(n -> n % 2 == 0)
    .map(n -> n * 10);

// Terminal collect() runs the pipeline and produces a concrete result
List<Integer> out = pipeline.collect(Collectors.toList()); // [20, 40]

// Same stream cannot be traversed again — second terminal throws
// pipeline.findFirst();  // IllegalStateException: stream has already been operated upon

// Need another pass? Open a new stream from the source:
long count = nums.stream().filter(n -> n % 2 == 0).count();

Short-circuiting

Operations like anyMatch can stop the pipeline early without consuming all elements. That is both a performance feature and a semantic feature when combined with infinite streams.

Can you use map instead of filter?

Not in the idiomatic sense: map must produce one output value per input (you could hack with Optional and flatMap, but that obscures intent). Interviewers ask this to see if you understand cardinality. Use filter to drop elements.

Answers: Multithreading

Multithreading

Multithreading means your process has more than one thread of execution sharing the same address space (heap). Threads run concurrently or in parallel depending on CPU cores and OS scheduling. Shared heap means two threads can read/write the same object fields—hence visibility and race conditions without synchronization.

Concurrency vs multithreading

Concurrency is a broader design concern: structuring a system so multiple tasks make progress, possibly via threads, thread pools, async I/O, reactive streams, or message passing. You can have concurrency on a single core via time-slicing. Multithreading is one implementation tool. Interviewers want you to say concurrency is about design; multithreading is about OS threads.

Two threads updating the same structure

Never use plain HashMap concurrently. Prefer ConcurrentHashMap for shared maps, AtomicInteger and friends for simple counters, or explicit ReentrantLock with small critical sections. Sometimes the best fix is no sharing: each thread owns data and passes messages through a queue. Spring services are often request-scoped per thread—still watch static fields and singletons with mutable state.

Thread-safe singleton

The enum singleton pattern is concise and JVM-safe: public enum Singleton { INSTANCE; ... }. Alternatives: eager initialization in a static field, or double-checked locking with volatile for lazy init (easy to get wrong). Avoid synchronization on every accessor if you can make initialization eager during app startup.

public enum Singleton { INSTANCE; public void doWork() {} }

Shallow vs deep copy

Shallow copy duplicates the top object but copies references to nested objects—both copies share the same nested instances. Deep copy duplicates nested graphs (expensive, must handle cycles). Cloneable in Java is tricky; often copy constructors or mapping libraries are clearer.

HashMap vs ConcurrentHashMap

HashMap is not synchronized; concurrent reads and writes risk infinite loops or corruption on old JDKs and lost updates logically. ConcurrentHashMap uses finer-grained locking and/or CAS operations for better throughput than wrapping with synchronizedMap. It also documents iterator weak consistency. API details like null keys differ—know your JDK version.

Answers: SQL

INNER JOIN vs LEFT JOIN

Joins combine rows from two tables based on a predicate, usually key equality. An INNER JOIN keeps only rows where the match succeeds on both sides—like the intersection of matching keys. A LEFT OUTER JOIN keeps every row from the left table and brings in right columns when a match exists; when there is no match, right-side columns appear as NULL. That is how you list all departments even if some have zero employees. RIGHT and FULL joins are less common in day-to-day reporting but follow the same idea mirrored.

-- INNER: only departments that have at least one employee row
SELECT d.dept_id, d.name, e.id AS emp_id, e.name AS emp_name
FROM departments d
INNER JOIN employees e ON e.dept_id = d.dept_id;

-- LEFT: every department; employee columns NULL if no one assigned
SELECT d.dept_id, d.name, e.id AS emp_id, e.name AS emp_name
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.dept_id;

WHERE vs HAVING

WHERE filters rows before grouping and aggregation. It cannot reference aggregate functions like COUNT(*) because those do not exist yet at that stage. HAVING filters groups after GROUP BY and aggregates are computed—use it for conditions like “departments with more than ten employees.” A common mistake is putting a group filter in WHERE and getting a syntax error or wrong logic.

-- WHERE: only rows with salary >= 50000 enter the aggregation
-- HAVING: only groups (depts) with more than 5 such employees
SELECT e.dept_id, COUNT(*) AS emp_cnt, AVG(e.salary) AS avg_sal
FROM employees e
WHERE e.salary >= 50000
GROUP BY e.dept_id
HAVING COUNT(*) > 5;

CASE expressions in WHERE

You can use a CASE expression anywhere an expression is allowed, including inside WHERE, as long as the overall predicate is boolean. Example: filter rows where a computed category matches a parameter. Some teams prefer readability by computing the CASE in a subquery or CTE first.

-- Rows classified by total; filter on that classification
SELECT order_id, customer_id, total
FROM orders
WHERE (CASE
         WHEN total > 1000 THEN 'HIGH'
         WHEN total > 100  THEN 'MED'
         ELSE 'LOW'
       END) = 'HIGH';

-- Same idea with a parameter-style literal (e.g. @tier from app)
-- WHERE CASE WHEN priority = 1 THEN 'URGENT' ELSE 'NORMAL' END = 'URGENT'

Indexing purpose

Indexes are auxiliary data structures (often B-trees) that let the engine find rows without scanning entire tables. They speed equality and range predicates and can help joins if the join keys are indexed. They cost disk space and slow down inserts/updates/deletes because the index must stay consistent. Choose columns that are selective (many distinct values) and appear in WHERE, JOIN, and ORDER BY clauses of heavy queries—exactly the kind of tuning you might cite from RodaBI reports.

-- Typical DDL (syntax varies slightly: SQL Server / MySQL / Postgres)
CREATE INDEX idx_employees_dept_id ON employees (dept_id);
CREATE INDEX idx_employees_hire_date ON employees (hire_date);

-- Query that can use idx_employees_dept_id (engine may choose index seek / nested loop join)
SELECT e.name, e.salary
FROM employees e
WHERE e.dept_id = 42;

Clustered vs non-clustered indexes

Clustered index defines how table rows are physically ordered on disk (or in the main storage structure). There is at most one clustered index per table: the leaf level is the table data (or contains the full row, depending on engine). In SQL Server, the primary key is often clustered by default. In MySQL InnoDB, the primary key is always clustered; secondary indexes store the PK columns in their leaves to find the row.

Non-clustered (secondary) indexes are separate B-tree structures: leaves hold the indexed key columns plus a pointer to the row (row id, or clustered key in SQL Server/InnoDB). Lookups may need an extra “bookmark lookup” / “back to table” step if the query asks for columns not in the index—unless the index covers the query.

-- SQL Server style: explicit clustered PK + nonclustered for seek on dept
CREATE TABLE employees (
  id INT NOT NULL PRIMARY KEY CLUSTERED,
  dept_id INT NOT NULL,
  hire_date DATE,
  name VARCHAR(100)
);
CREATE NONCLUSTERED INDEX ix_emp_dept ON employees (dept_id);

-- MySQL InnoDB: PRIMARY KEY is clustered; others are secondary
CREATE TABLE employees (
  id INT NOT NULL PRIMARY KEY,
  dept_id INT NOT NULL,
  hire_date DATE,
  name VARCHAR(100),
  INDEX ix_dept (dept_id)
);

How the index is evaluated (order and “which side”)

A classic B-tree is evaluated top-down: start at the root, compare the search key with keys in the node, follow the child pointer (left / middle / right—conceptually “which side” of the split) until you reach a leaf. An equality seek stops at matching leaves; a range (>, BETWEEN, ORDER BY range) often seeks to the start key then scans forward along the leaf chain (left-to-right in key order). The optimizer’s execution plan shows Index Seek vs Index Scan vs RID Lookup—that is the practical “order” you discuss in interviews.

For a composite index (col1, col2, col3), the tree is ordered first by col1, then col2 within equal col1, then col3. The engine still walks root → leaf; the leftmost prefix rule (below) decides how much of that structure is usable for a given query.

Composite index with 3 columns — query uses only 2

This is usually fine if those two columns form a leading prefix of the index. Index (dept_id, hire_date, last_name) can support WHERE dept_id = 1 AND hire_date = '2024-01-01' well: both are leading columns. It can also support WHERE dept_id = 1 alone (one leading column). It does not fully use the tree for WHERE hire_date = … AND last_name = … without an equality on dept_id, because you cannot skip the first key in the sort order—often a scan or a different index is chosen.

Query has 3 predicates — index has only 2 columns

The engine may still use the two-column index to narrow rows (index seek + partial filter), then apply the third predicate as a residual filter on those rows (in the engine or after lookup). If the third column is highly selective, a three-column index might be better. If the first two already reduce rows enough, the two-column index may be optimal.

Same 3 columns — different order in WHERE vs in CREATE INDEX

For simple AND predicates, SQL does not care about the textual order in the query: WHERE a = 1 AND b = 2 AND c = 3 is the same as WHERE c = 3 AND a = 1 AND b = 2. The optimizer reorders evaluation. What matters is the index definition order (a, b, c) and whether your predicates match a leftmost prefix with sensible operators (equality on leading columns before a range on the next column). OR across columns, functions on indexed columns like WHERE YEAR(hire_date) = 2024, or implicit conversions often prevent or limit index use regardless of WHERE clause order.

-- Composite index (order in DDL is what matters)
CREATE INDEX ix_emp_dept_hire_name
  ON employees (dept_id, hire_date, last_name);

-- Uses leading dept_id + hire_date (index seek on prefix)
SELECT * FROM employees
WHERE hire_date = '2024-06-01' AND dept_id = 10;

-- Same as above: predicate order in SQL does not change index matching
SELECT * FROM employees
WHERE dept_id = 10 AND hire_date = '2024-06-01';

-- Cannot use ix_emp_dept_hire_name for seek on hire_date alone (skipped leading dept_id)
-- (engine may index scan or use another index)
SELECT * FROM employees WHERE hire_date = '2024-06-01';

Employee count per department

The query below uses LEFT JOIN so departments with zero employees still appear with a count of zero (depending on COUNT usage—counting a non-null column vs COUNT(*) differs slightly). Using COUNT(e.employee_id) excludes null employee rows from the count.

SELECT d.dept_id, d.name, COUNT(e.employee_id) AS cnt
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.dept_id
GROUP BY d.dept_id, d.name;

Maximum salary patterns

SELECT MAX(salary) FROM employees returns one aggregate. If you need the whole row(s) for highest earners, use a window function (RANK() OVER (ORDER BY salary DESC)) in databases that support them, or a subquery comparing to MAX(salary), or ORDER BY salary DESC LIMIT 1 knowing ties need extra handling.

-- Scalar max only
SELECT MAX(salary) AS top_salary FROM employees;

-- All employee rows tied at max salary
SELECT e.*
FROM employees e
WHERE e.salary = (SELECT MAX(salary) FROM employees);

-- Window: rank by salary; take rank 1 (handle ties with DENSE_RANK if needed)
SELECT id, name, salary
FROM (
  SELECT id, name, salary,
         RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) x
WHERE rnk = 1;

-- Simple “one row” (ties arbitrary) — MySQL/Postgres style
SELECT id, name, salary FROM employees ORDER BY salary DESC LIMIT 1;

Changing ENUM values at “runtime”

In MySQL, ENUM is part of the table definition. Adding or renaming enum labels is a schema change (ALTER TABLE), not something you do with a normal UPDATE to “redefine” the enum type. In Java, enums are fixed at compile time. If you need dynamic labels, store codes in a lookup table instead.

-- MySQL: extend allowed labels (migration / DBA operation — not app “runtime”)
ALTER TABLE orders
  MODIFY COLUMN status ENUM('PENDING','SHIPPED','DELIVERED','CANCELLED') NOT NULL;

-- Prefer flexible design: status as FK to lookup table
-- CREATE TABLE order_status (code VARCHAR(20) PRIMARY KEY, label VARCHAR(50));
-- orders.status_code REFERENCES order_status(code);

ACID principles (relational databases)

ACID describes what users expect from a transaction—a group of SQL statements that should behave as one unit.

Atomicity: Either all changes in the transaction are saved, or none are. If anything fails or you run ROLLBACK, the database leaves no half-finished transfer (no money taken without money added).

Consistency: After the transaction, the database still obeys all rules you defined—foreign keys, unique constraints, check constraints, and business rules enforced in triggers or app code. The transaction moves from one valid state to another.

Isolation: Transactions running at the same time should not see each other’s unfinished work in ways that break your expectations. Real engines use isolation levels (e.g. Read Committed, Repeatable Read, Serializable) that trade strictness for performance. Symptoms when isolation is “weaker” include dirty reads, non-repeatable reads, or phantom rows—worth naming in interviews.

Durability: After COMMIT, the database promises the data survives a normal crash (written to disk or replication log). It does not mean “impossible to lose data in every disaster”—backups and replication still matter.

-- Pattern: transfer money — both updates succeed or neither does
BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
  -- if a constraint fails or you ROLLBACK; nothing is committed
COMMIT;

Syntax varies: SQL Server often uses BEGIN TRAN / COMMIT; Oracle auto-commits unless you open an explicit transaction; JDBC/Spring usually wrap this for you with @Transactional.

Table partitioning (one database, split storage)

Partitioning splits one logical table into separate physical pieces (partitions) inside the same database server/cluster. A common key is time (month/year of events) or region. The optimizer can skip whole partitions when your WHERE clause matches the partition key—partition pruning—so scans are cheaper than reading one giant table.

Types you may mention: RANGE (dates, ids), LIST (country codes), HASH (spread rows evenly when there is no natural range). Partitioning is not the same as sharding: you still have one DB instance managing the table (or one cluster), and cross-partition queries are still possible in SQL.

-- PostgreSQL: parent table + range partitions (simplified)
CREATE TABLE events (
  id          bigserial,
  created_at  timestamptz NOT NULL,
  payload     jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2024 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE events_2025 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Query touches only relevant partition(s) when possible
SELECT COUNT(*) FROM events WHERE created_at >= '2025-06-01';
-- MySQL: RANGE on expression (example)
CREATE TABLE sales (
  id INT NOT NULL,
  sale_date DATE NOT NULL,
  amount DECIMAL(12,2),
  PRIMARY KEY (id, sale_date)
) PARTITION BY RANGE (YEAR(sale_date)) (
  PARTITION p2023 VALUES LESS THAN (2024),
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p_future VALUES LESS THAN MAXVALUE
);

Sharding (many databases, split by key)

Sharding (horizontal scaling) splits data across many separate databases (often on different machines). Each shard holds a subset of rows, usually chosen by a shard key—for example tenant_id, user_id, or geographic region. A router (app layer, proxy, or gateway) sends each query to the correct shard. Sharding helps when one server cannot hold the data or handle the write load.

Tradeoffs: Joins and transactions that span shards are hard—you may need distributed transactions (heavy), eventual consistency, or denormalized data per shard. Rebalancing when shards grow (split/move data) is operational work. Interview sound bite: “Partitioning divides a table inside one engine; sharding divides the database across nodes.”

-- Sharding is mostly application/router config, not one standard SQL statement.
-- Example: route by hash of user_id
-- shard = hash(user_id) % NUM_SHARDS
-- JDBC URL or connection pool picks datasource for that shard.

-- Same logical table exists on each shard with the same schema:
-- shard0.users, shard1.users, ... each holds different user_id ranges.

-- Cross-shard query (aggregate all users) = fan-out to every shard + merge in app,
-- or use a separate analytics/warehouse fed by CDC.

Answers: Design patterns

Factory pattern

A factory centralizes object creation so callers depend on interfaces or abstract types, not concrete classes. That matters when construction is conditional (pick Xero vs QuickBooks client), involves configuration, or must enforce invariants before returning the object. In your resume context, an “accounting connector factory” is a credible real-world example: the rest of the app asks for a connector by provider name or tenant configuration.

Strategy pattern

Strategy encapsulates a family of interchangeable algorithms behind one interface. The context class (checkout, pricing, notification) delegates to the strategy interface. Spring’s dependency injection makes strategies natural: inject NotificationStrategy implementations or use a map of strategies keyed by type. Dealdiva-style features (different deal scoring or referral rules) map well to strategy if you want a clean interview story.

import java.nio.charset.StandardCharsets;

// Domain object the exporters work on
public final class Invoice {
  private final String id;
  private final String customerName;
  private final double total;

  public Invoice(String id, String customerName, double total) {
    this.id = id;
    this.customerName = customerName;
    this.total = total;
  }
  public String getId() { return id; }
  public String getCustomerName() { return customerName; }
  public double getTotal() { return total; }
}

// Product interface — callers depend on this, not on PDF vs CSV
public interface InvoiceExporter {
  byte[] export(Invoice inv);
}

public final class PdfExporter implements InvoiceExporter {
  @Override
  public byte[] export(Invoice inv) {
    // Real code would build PDF bytes (e.g. iText, OpenPDF, Apache PDFBox)
    String stub = "PDF export for invoice " + inv.getId()
        + " (" + inv.getCustomerName() + ") total=" + inv.getTotal();
    return stub.getBytes(StandardCharsets.UTF_8);
  }
}

public final class CsvExporter implements InvoiceExporter {
  @Override
  public byte[] export(Invoice inv) {
    String csv = "id,customer,total\n"
        + inv.getId() + ","
        + inv.getCustomerName().replace(",", " ") + ","
        + inv.getTotal() + "\n";
    return csv.getBytes(StandardCharsets.UTF_8);
  }
}

// Factory: one place that chooses concrete exporter from a key / config
public final class InvoiceExporterFactory {
  public InvoiceExporter get(String type) {
    return switch (type.toUpperCase()) {
      case "PDF" -> new PdfExporter();
      case "CSV" -> new CsvExporter();
      default -> throw new IllegalArgumentException("Unknown export type: " + type);
    };
  }
}

// Caller never references PdfExporter / CsvExporter directly
class BillingService {
  private final InvoiceExporterFactory exporterFactory;

  BillingService(InvoiceExporterFactory exporterFactory) {
    this.exporterFactory = exporterFactory;
  }

  byte[] downloadInvoice(String format, Invoice invoice) {
    InvoiceExporter exporter = exporterFactory.get(format);
    return exporter.export(invoice);
  }
}

Answers: Spring & Spring Boot

Spring vs Spring Boot

Classic Spring Framework is the programming and configuration model: IoC container, AOP, transaction abstraction, MVC, etc. Spring Boot is an opinionated layer that auto-configures those pieces based on classpath, provides starters (dependency bundles), embeds Tomcat/Jetty/Undertow, and adds production features like Actuator endpoints. You still write Spring beans and use Spring APIs; Boot removes most XML and reduces boilerplate.

@Controller vs @RestController

@Controller marks a web MVC controller whose methods return view names unless annotated per method with @ResponseBody. @RestController combines @Controller and @ResponseBody so return values serialize directly to JSON/XML via HTTP message converters—typical for APIs you built in RodaBI and Dealdiva.

Inversion of Control and Dependency Injection

IoC means your objects do not assemble their own dependencies with new everywhere; the Spring container constructs the graph. DI is how dependencies arrive: constructor injection (preferred), setter injection, or field injection (discouraged in purist style but common). Benefits: testability (swap mocks), single responsibility, and configuration centralization.

Circular dependencies

If bean A’s constructor needs B and B’s constructor needs A, Spring cannot instantiate either. Setter/field injection can sometimes break the cycle but hides design smells. Better fixes: extract a third collaborator, introduce an interface boundary, use events, or apply @Lazy on one injection point so a proxy is injected first. The best answer in interviews is “we refactored to remove the cycle.”

Spring Boot application lifecycle

At startup, Spring Boot creates the application context, runs auto-configuration, starts the embedded web server (for web apps), and invokes ApplicationRunner or CommandLineRunner beans. Shutdown hooks close the context gracefully so connections and thread pools release cleanly.

Global exception handling

@ControllerAdvice / @RestControllerAdvice centralizes exception translation so controllers stay thin and clients always receive consistent error shapes (status code, message, optional field errors). Handlers map exception types to HTTP semantics: not found → 404, validation → 400, conflict → 409, unexpected → 500 without leaking stack traces publicly.

@RestControllerAdvice
public class RestExceptionHandler {
  @ExceptionHandler(EntityNotFoundException.class)
  public ResponseEntity<ProblemDetail> notFound(EntityNotFoundException ex) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(404, ex.getMessage());
    return ResponseEntity.status(404).body(pd);
  }
}

Custom repository query

Spring Data derives simple queries from method names, but reports and eager loading often need @Query with JPQL or native SQL. join fetch in JPQL loads associations in the same query to avoid N+1 when you know you need them. Use DTO projections (interface-based or class-based) when you do not want full entities returned to the web layer.

public interface OrderRepository extends JpaRepository<Order, Long> {
  @Query("select o from Order o join fetch o.lines where o.orgId = :orgId")
  List<Order> findWithLinesForOrg(@Param("orgId") Long orgId);
}

Spring Beans (scopes, @Bean, lifecycle)

Bean scopes and duplicate bean types

A scope answers: “How many objects does Spring create, and how long do they live?” Most beans are singleton by default: one shared object for the app. Prototype gives a fresh object when requested. In web apps, request creates one bean per HTTP request and session creates one per user session.

Two beans of the same type: If two classes implement NotificationSender and a constructor asks for only NotificationSender, Spring cannot guess which one you want. Pick a default with @Primary, choose explicitly with @Qualifier, or inject by bean name via @Resource(name = "...").

@Service @Primary
public class EmailNotificationSender implements NotificationSender { /* ... */ }

@Service
@Qualifier("sms")
public class SmsNotificationSender implements NotificationSender { /* ... */ }

@Service
public class AlertService {
  private final NotificationSender email;   // @Primary wins if no qualifier
  private final NotificationSender sms;

  public AlertService(NotificationSender email,
                      @Qualifier("sms") NotificationSender sms) {
    this.email = email;
    this.sms = sms;
  }
}

@SpringBootApplication and @Bean

@SpringBootApplication combines @Configuration, @EnableAutoConfiguration, and @ComponentScan. Use @Bean methods in a @Configuration class when you need to register third-party or custom-built objects you cannot annotate with @Component.

Bean lifecycle callbacks

Bean lifecycle (short version): instantiate bean, inject dependencies, run init callbacks (@PostConstruct), bean is ready, then run destroy callbacks (@PreDestroy) during shutdown. BeanPostProcessor can wrap beans before/after initialization for cross-cutting behavior.

Answers: Security & APIs

Authentication vs authorization

Authentication establishes identity: “this request is user 42.” It happens via passwords, MFA, SSO, or tokens. Authorization decides what that identity may do: “user 42 may read reports but not delete tenants.” Spring Security separates these in the filter chain: first establish an Authentication object, then evaluate access rules against it.

POST vs PUT

HTTP verbs are hints, not laws, but interviews expect the REST-leaning story. POST to a collection URI often creates a new resource whose identifier the server assigns; repeated POSTs may create duplicates (not idempotent). PUT to a resource URI replaces the representation at that known identifier and is often described as idempotent in intent (repeating with the same body should land the same state). PATCH is partial update. Real APIs sometimes bend these rules—be ready to mention your actual conventions.

JWT vs OAuth 2

OAuth 2 is an authorization framework with grant types (authorization code, client credentials, refresh tokens). It defines how clients obtain tokens from an authorization server. JWT (JSON Web Token) is a compact, signed (or MAC’d) token format that can carry claims like subject, expiry, and roles. An OAuth access token may be a JWT or an opaque string that only the authorization server can introspect. Conflating “OAuth token” and “JWT” is a common interview trap—clarify the distinction.

Signing and verifying JWTs

A JWT has three base64url-encoded parts: header (algorithm, type), payload (claims), signature. Signing with HMAC uses a shared secret—simple but secret distribution is sensitive. RSA/ECDSA uses a private key to sign and a public key to verify—good for services that only need to verify, not mint, tokens. Verification must check the signature, that exp is in the future, and optionally nbf, iss, and aud. Decoding without verifying is not security.

Gateway-level authentication

An API gateway terminates TLS, authenticates the caller once, and forwards trust to internal services—often by attaching headers like user id and scopes after validation. That avoids every microservice parsing JWTs independently (though many still do). Gateways also enforce rate limits, request size, IP allowlists, and sometimes request/response transformation.

RBAC in Spring

Role-based access control maps users to roles and roles to permissions. In Spring Security, roles are often modeled as GrantedAuthority entries (sometimes prefixed ROLE_). Method security with @PreAuthorize keeps rules close to sensitive service methods. Remember: always enforce authorization on the server—UI hiding a button is not security.

Rate limiting APIs

Protect backends from abuse and accidental storms with per-client quotas. Implementations include API gateway plugins, Redis-backed token buckets, or libraries like Resilience4j’s rate limiter. Combine with timeouts and bulkheads so one noisy tenant cannot exhaust thread pools.

Answers: JPA & Hibernate

JPA vs Hibernate

JPA is a Java specification (interfaces and annotations) for object-relational mapping. Hibernate is the dominant implementation used by Spring Boot’s spring-boot-starter-data-jpa. You program to JPA APIs; Hibernate provides SQL generation, caching hooks, and dialect-specific optimizations. Occasionally you use Hibernate-specific annotations when JPA lacks a feature.

Lazy loading vs eager fetching

Lazy associations load when you first traverse them inside an active persistence context (typically an open transaction/session). If you load 100 parents and then touch a lazy collection on each, you may trigger the N+1 query problem: one query for parents and N for each collection. Mitigations: fetch joins in JPQL, entity graphs, DTO projections, or batch fetching configuration. Eager fetching loads associations with the root query—convenient but can explode row counts (cartesian products) if multiple collections are eager-fetched together.

@JoinColumn

On the owning side of a many-to-one or one-to-one, @JoinColumn names the foreign key column in the owner’s table pointing to the related table. It is how JPA knows which column implements the association in the database.

@JoinTable for many-to-many

When both sides can have collections and the relational model uses a junction table, @JoinTable names that table and maps join columns for the owner and inverse side. Hibernate generates or expects the join table schema accordingly.

@ManyToMany
@JoinTable(
  name = "user_role",
  joinColumns = @JoinColumn(name = "user_id"),
  inverseJoinColumns = @JoinColumn(name = "role_id"))
private Set<Role> roles;

SessionFactory, Session, and first-level cache

In Hibernate, a SessionFactory is expensive to create and is application-scoped; it holds metadata about entities and connection pooling integration. A Session (JPA EntityManager under the hood) is a unit-of-work scoped object, usually aligned with a database transaction. The session’s persistence context is the first-level cache: loading an entity by id twice in the same session typically hits memory, not the database. When the session closes, detached entities need merging to persist further changes.

Second-level and query cache

The second-level cache shares entity state across sessions using a provider like EHCache or Infinispan. It requires explicit configuration of cache regions and concurrency strategies and is easy to misuse if data changes frequently. The query cache caches the result list of a query (often as ids pointing into the entity cache). It invalidates incorrectly if you do not understand update timestamps—many teams disable it unless they have a clear read-mostly workload.

Answers: Microservices & messaging

Loose coupling

Loose coupling means services can evolve and deploy independently without breaking others. You achieve it with stable API contracts (versioned REST/OpenAPI), asynchronous events for non-critical paths, and avoiding a shared database schema as the integration point (which creates tight transactional coupling). Contracts should be tested with consumer-driven contract tests where possible.

API Gateway

Gateways provide a single entry for external clients, centralizing cross-cutting concerns: authentication, TLS, routing to internal services, rate limiting, and sometimes response aggregation (BFF pattern). Internally, service-to-service calls may bypass the public gateway or use an internal mesh/gateway depending on architecture.

gRPC

gRPC uses HTTP/2 and Protocol Buffers for compact, strongly typed contracts. It suits internal high-performance RPC. Browsers do not speak gRPC natively, so public-facing apps often use REST/GraphQL at the edge and gRPC behind the gateway.

Kafka

Kafka models an append-only log partitioned by key. Producers append events; consumers read with offsets; consumer groups scale processing horizontally. Retention enables replay and audit. It shines for event streaming and high throughput; operational complexity is higher than a traditional broker.

RabbitMQ (aligned with your resume)

RabbitMQ is a message broker centered on exchanges and queues. Producers publish to an exchange with a routing key; bindings route messages into queues; consumers compete or fan out depending on topology. Acknowledgements and publisher confirms give reliability. Dead-letter exchanges handle poison messages. It is excellent for task queues and work distribution—exactly the kind of setup you might run in Docker alongside services.

Alternatives to Kafka and RabbitMQ

Cloud-managed queues (Azure Service Bus, AWS SQS/SNS), Redis Streams, NATS, and Apache Pulsar each trade off persistence, ordering guarantees, ops burden, and cost. Interview credit comes from naming the tradeoff, not from listing ten products.

CQRS read/write URLs across environments

Never hardcode four environment URLs in source. Use Spring profiles (application-prod.yml), environment variables injected at deploy time, or a secret store like Azure Key Vault. Spring Cloud Config can centralize YAML per repo and environment. The pattern is “same code, different configuration per environment.”

Resilience4j

Resilience4j implements resilience patterns as decorators: circuit breakers stop calling failing dependencies, retries with backoff handle transient errors, bulkheads limit concurrent calls, time limiters cap wait time, rate limiters cap call frequency. Combine with timeouts everywhere a remote call exists.

Saga pattern

Distributed transactions across services cannot rely on a single two-phase commit across arbitrary databases. A saga breaks the business process into local transactions with compensating actions if a later step fails. Orchestration uses a central coordinator; choreography uses events between services. You accept eventual consistency and must design idempotent handlers.

When a downstream service is down

Without mitigation, threads block, thread pools exhaust, and cascading failures take down callers. Mitigations: short timeouts, circuit breakers to fail fast, cached fallbacks where safe, retries only for idempotent operations with exponential backoff and jitter, and asynchronous processing with durable queues so work is not lost when a peer is temporarily unavailable.

Answers: DevOps, Azure, CORS

Deployment strategies (rolling, blue-green / red-black, canary, shadow, recreate)

These patterns trade off risk, cost (extra capacity), rollback speed, and observability. Production systems often combine them (e.g. blue-green for the platform, canary for individual services behind a mesh).

Rolling deployment

Instances (or pods) are updated in place in waves: drain one, replace with new version, health-check, move to the next. Traffic gradually shifts as new nodes join the pool. Pros: no second full stack needed, simple for stateless apps. Cons: old and new versions run at the same time during the rollout—schemas and APIs must stay backward compatible across that window. Rollback is slower (re-roll) unless you keep previous images ready.

Blue-green deployment

You run two complete environments: blue (current live) and green (new release), each able to take 100% of traffic. Green is deployed and smoke-tested while blue still serves users. You switch the load balancer or DNS to green in one step; rollback is switching back to blue. Pros: fast cutover and fast rollback, clear “all or nothing” release. Cons: roughly double infrastructure during cutover; migrations must not break the idle stack if you might roll back (expand/contract migrations, feature flags).

Red-black deployment

Red-black is the same idea as blue-green—two identical stacks, one active (say “red” live) and one idle (“black”) holding the new version, then traffic flips. Some platforms (e.g. Netflix Spinnaker, some Kubernetes docs) use red/black wording instead of blue/green. In interviews you can say: “red-black is blue-green under another name—dual full environments with instant traffic switch.”

Canary deployment

A canary sends a small slice of real traffic (e.g. 1–5%) to the new version while the majority stays on stable. You watch metrics: error rate, latency, saturation, business KPIs. If healthy, you ramp the percentage (10% → 25% → 50% → 100%) or abort and drain the canary. Pros: limits blast radius, validates under real load. Cons: needs good observability and often routing (service mesh, LB weights, feature flags by user cohort). You must handle schema compatibility while both versions serve traffic.

Shadow deployment (dark traffic / shadow mode)

Shadow sends a copy of production requests to the new version without returning its response to the user—the client still gets the answer from the stable version. The shadow service may execute read-only logic or write to a test store; you compare latency, errors, or response bodies offline. Pros: exercise new code under real volume with zero user impact (when done safely). Cons: doubled work can load dependencies; must avoid double side effects (duplicate payments, emails) unless the shadow path is strictly non-mutating or uses mocked sinks. Often implemented with a proxy or mesh duplicating requests.

Recreate deployment

Tear down the old stack, then start the new one—downtime in between. Acceptable for dev/small internal tools; rare for customer-facing APIs.

Logging and metrics

Use structured logging (JSON) with correlation IDs propagated across services (often via headers) so you can trace one user action through many calls. CI/CD and SonarCloud

A typical pipeline builds artifacts, runs unit and integration tests, runs static analysis and coverage thresholds (SonarCloud quality gate), scans dependencies for CVEs, then deploys to an environment. Failing fast on quality gates prevents accumulating debt.

CORS

Browsers enforce the Same-Origin Policy. Cross-origin AJAX calls need server consent via CORS headers like Access-Control-Allow-Origin. “Simple” requests go straight; others trigger a preflight OPTIONS request. The server must respond correctly to preflight. CORS is a browser concern—non-browser clients (server-to-server) ignore it.

Unit testing

A unit test verifies a small piece of logic in isolation, fast and deterministic. Answers: React & TypeScript

Caching in React apps

Caching happens at many layers. The browser honors HTTP headers (Cache-Control, ETag) for static assets and sometimes API responses. CDNs cache public assets geographically close to users. Client libraries like React Query or SWR cache API JSON in memory, dedupe requests, and offer stale-while-revalidate UX. useMemo and React.memo cache render work, not network data. Service workers can cache shell HTML/JS for offline PWAs. Redux stores can act as a normalized entity cache if you hydrate it from APIs and reuse selectors.

Cancelling async work when the user navigates away

When a component mounts, useEffect may start a fetch. If the user navigates away before completion, setting state on an unmounted component triggers warnings and can show stale data on a new screen. The fix is an AbortController passed to fetch (or axios cancel tokens) and aborting in the effect cleanup. Another pattern is a boolean “is current” flag ignored on late responses. Libraries like React Query cancel in-flight queries on query key change or unmount by default when configured.

useEffect(() => {
  const ac = new AbortController();
  fetch("/api/data", { signal: ac.signal })
    .then(r => r.json())
    .then(setData)
    .catch(e => { if (e.name !== "AbortError") console.error(e); });
  return () => ac.abort();
}, []);

Nullish coalescing (??) vs logical OR (||)

The ?? operator returns the right side only when the left is null or undefined. The || operator returns the right side for any falsy value on the left, including 0, "", and false. That distinction matters for UI defaults: a valid numeric zero should not be replaced by a default if you use || incorrectly.

preventDefault on form submit

Classic HTML forms post to the server and reload the page. In SPAs you intercept onSubmit, call event.preventDefault(), validate client-side, then call your API with fetch or axios. Without preventDefault, the browser performs a full navigation and you lose the SPA experience.

Event bubbling and capturing

DOM events propagate in phases: capture from window down to target, then bubble from target up. Most handlers use bubbling. stopPropagation prevents further propagation; stopImmediatePropagation also blocks other listeners on the same element. React historically pooled synthetic events (older versions); modern React attaches listeners differently—still understand bubbling for nested interactive elements.

Props drilling vs lifting state

Props drilling passes data through many layers of components that do not care about the data except to forward it—verbose and brittle. Lifting state up moves shared state to the nearest common ancestor so each child receives only what it needs. For app-wide concerns (auth user, theme), Context or Redux avoids deep drilling.

Arrow functions vs traditional functions

Arrow functions do not have their own this; they close over the enclosing lexical this. Traditional functions have dynamic this based on call site—important in old class components where you bound methods in constructors. In functional components with hooks, this largely disappears; arrows are common for inline handlers. Arrow functions are not hoisted like function declarations.

Promises and async/await

Promises represent future values. Chaining with then/catch composes asynchronous steps. async/await is syntactic sugar that pauses an async function until a Promise settles, while still running on the event loop (not blocking threads). Use Promise.all for independent parallel tasks; Promise.allSettled when you need every outcome; race for timeouts.

Redundant nested awaits

If function A calls B and B calls C, and all are async, you do not need to sprinkle await on every wrapper if only the innermost operation is asynchronous—flatten to one async function that awaits the real I/O once, or return the Promise without awaiting intermediate wrappers. Excess awaits serialize work unnecessarily and obscure error boundaries.

useEffect and the dependency array

useEffect runs after the browser paints the DOM update from render. The dependency array lists reactive values whose changes should re-run the effect. An empty array means “run once on mount.” Omitting the array means “run after every render” (usually a bug). Cleanup functions unsubscribe sockets, clear timers, or abort fetches when dependencies change or the component unmounts. ESLint’s exhaustive-deps rule exists because missing dependencies cause stale closures.

Custom hooks

A custom hook is any function named useSomething that calls other hooks. It extracts repeated stateful logic (form state, data fetching patterns, debouncing) so components stay readable. Hooks must be called unconditionally at the top level of a React function—never inside loops or conditionals.

Redux data flow

UI dispatches a plain action object. The root reducer function (possibly combined from slices) computes the next immutable state. The store notifies subscribers; React-Redux re-renders connected components. Middleware like Redux Thunk or RTK Query handles async side effects outside reducers, keeping reducers pure.

Answers: DS & algorithms

How HashMap places keys and handles collisions

When you put(key, value), Java computes key.hashCode(), applies supplemental hashing and array index transformation to choose a bucket index. If the bucket is empty, the entry stores directly. If another entry exists, equals determines whether the key is the same (replace value) or a collision (chain). Since Java 8, when a bucket grows long, entries may be organized in a balanced tree keyed by compareTo or tie-breaker hash to keep worst-case behavior better than a long linear chain. This ties directly to why equals and hashCode must be consistent.

TreeSet vs HashSet

HashSet stores elements in hash buckets with average O(1) add/contains; iteration order is undefined. TreeSet is a red-black tree sorted by natural order or a Comparator; operations are O(log n) but you gain sorted traversal and range queries. Choose tree when ordering matters; hash when only membership matters.

// HashSet: fast membership; order not guaranteed (do not rely on toString order)
Set<Integer> hash = new HashSet<>();
hash.add(30); hash.add(10); hash.add(20);
System.out.println(hash);  // e.g. [20, 10, 30] — arbitrary

// TreeSet: always sorted (natural order for Integer)
Set<Integer> tree = new TreeSet<>();
tree.add(30); tree.add(10); tree.add(20);
System.out.println(tree);   // [10, 20, 30]

// TreeSet with custom order (longest String first)
Set<String> byLength = new TreeSet<>(
    Comparator.comparingInt(String::length).reversed()
        .thenComparing(Comparator.naturalOrder()));
byLength.add("a"); byLength.add("bbb"); byLength.add("bb");
// iteration visits "bbb", then "bb", then "a"

HashSet vs HashMap

HashSet is backed by a HashMap internally: elements are keys mapped to a dummy value. HashMap maps keys to meaningful values. Interviewers want you to say sets enforce uniqueness of elements; maps enforce uniqueness of keys with associated values.

// HashSet: "is this value already in the collection?" — no value payload
Set<String> tags = new HashSet<>();
tags.add("java");
tags.add("java");           // duplicate ignored; add returns false second time
System.out.println(tags.size());  // 1

// HashMap: unique key → associated value (lookup by key)
Map<String, String> userEmail = new HashMap<>();
userEmail.put("alice", "alice@example.com");
userEmail.put("bob", "bob@example.com");
String email = userEmail.get("alice");  // "alice@example.com"

// Same keys could drive a set of ids and a map of id → row
Set<Long> activeUserIds = new HashSet<>();   // only "who"
Map<Long, String> idToName = new HashMap<>(); // "who" → "display name"

Palindrome and anagram problems

A palindrome reads the same forward and backward. The two-pointer technique from both ends compares characters in O(n) time and O(1) extra space for ASCII strings. Anagrams are permutations with the same character counts—use a frequency table or sort both strings (O(n log n)). Choose the approach that matches constraints (Unicode, large alphabet).

// --- Palindrome: two pointers, O(n) time, O(1) extra space ---
static boolean isPalindrome(String s) {
  int i = 0, j = s.length() - 1;
  while (i < j) {
    if (s.charAt(i) != s.charAt(j)) return false;
    i++;
    j--;
  }
  return true;
}
// isPalindrome("racecar") → true   isPalindrome("hello") → false

// Common variant: ignore case and non-letters (e.g. "A man, a plan, a canal: Panama")
static boolean isPalindromePhrase(String s) {
  int i = 0, j = s.length() - 1;
  while (i < j) {
    while (i < j && !Character.isLetterOrDigit(s.charAt(i))) i++;
    while (i < j && !Character.isLetterOrDigit(s.charAt(j))) j--;
    if (Character.toLowerCase(s.charAt(i)) != Character.toLowerCase(s.charAt(j)))
      return false;
    i++;
    j--;
  }
  return true;
}
// --- Anagram: same multiset of characters (permutation) ---

// Frequency table, O(n), O(1) space if alphabet fixed (e.g. lowercase a–z)
static boolean isAnagramLetters(String a, String b) {
  if (a.length() != b.length()) return false;
  int[] count = new int[26];
  for (int i = 0; i < a.length(); i++) {
    count[a.charAt(i) - 'a']++;
    count[b.charAt(i) - 'a']--;
  }
  for (int v : count) if (v != 0) return false;
  return true;
}

// General Unicode / mixed chars: use HashMap<Character, Integer> the same way,
// or sort both strings and compare (O(n log n), simple to code)
static boolean isAnagramSort(String a, String b) {
  if (a.length() != b.length()) return false;
  char[] ca = a.toCharArray();
  char[] cb = b.toCharArray();
  java.util.Arrays.sort(ca);
  java.util.Arrays.sort(cb);
  return java.util.Arrays.equals(ca, cb);
}

Reversing a linked list (iterative, three pointers)

Singly linked lists only traverse forward. Reversal rewires each node’s next to point to the previous node. Maintain three references: prev (starts null), curr (starts at head), and next (temporary hold of curr.next before you break the link). Each iteration: save next = curr.next, set curr.next = prev, advance prev = curr and curr = next. When curr is null, prev is the new head. This is O(n) time and O(1) space. The recursive version uses O(n) call stack space—mention stack overflow risk on huge lists.

Node reverse(Node head) {
  Node prev = null, curr = head;
  while (curr != null) {
    Node next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }
  return prev;
}

Swapping integers without a temporary variable

XOR swap tricks exist (a ^= b; b ^= a; a ^= b;) but are mostly academic: they fail if a and b alias the same memory location, and they obscure intent. Arithmetic swaps with overflow risk are also discouraged. In interviews, mention them briefly then say production code uses a temp variable or Collections.swap for clarity.

Answers: SDLC, SOLID, ACID, leadership

Software development lifecycle

SDLC is the journey from idea to running software: gather requirements, analyze constraints, design architecture and interfaces, implement in iterations, test at multiple levels, deploy to environments with checks, then operate—monitoring, incidents, and feeding learnings back into requirements. Agile teams compress these phases into sprints but the concerns still exist.

SOLID principles explained

Single Responsibility: A class should have one reason to change—separate reporting from authorization. Open/Closed: Extend behavior (new strategies) without editing stable core code. Liskov Substitution: Subtypes must honor the contract of the base type—do not throw unexpected exceptions or weaken postconditions. Interface Segregation: Many small interfaces beat one fat interface that forces dummy implementations. Dependency Inversion: High-level modules depend on abstractions; Spring injects implementations.

SOLID example from your world

A NotificationService depends on a Notifier interface. Email, SMS, and in-app notifiers are separate classes. Adding Slack does not require editing the orchestration logic—only wiring a new bean. That illustrates Open/Closed and Dependency Inversion together.

ACID in databases

Atomicity: Transactions commit entirely or roll back entirely. Consistency: Constraints and rules hold before and after the transaction (foreign keys, checks). Isolation: Concurrent transactions do not see each other’s partial work at wrong isolation levels—tradeoffs versus performance. Durability: Committed data survives crashes once the DB acknowledges commit (WAL, replication).

Answers: Architecture, ERD, realtime

Application architectures

Layered architecture stacks presentation, application/services, domain, and persistence—simple and common in Spring apps. Hexagonal (ports and adapters) emphasizes interfaces (“ports”) with swappable infrastructure (“adapters”) for testing. Microservices split bounded contexts into deployable units with network contracts. CQRS separates read and write models when access patterns or scale differ; event sourcing stores changes as events—powerful but operationally heavy.

ERD (entity-relationship diagrams)

ERDs show entities (tables), attributes, primary keys, foreign keys, and cardinalities: one-to-one, one-to-many, many-to-many (resolved with a junction table). They communicate schema intent to both engineers and stakeholders and guide index design.

Session management on the web

Classic sessions store server-side state keyed by a session cookie. JWT-based auth moves state into signed tokens; servers validate signature and claims each request—stateless for the server but revocation and token size need planning. Refresh tokens rotate access tokens; store tokens securely (httpOnly cookies mitigate XSS theft vs localStorage tradeoffs). Always combine transport security (HTTPS) with sensible expiry.

Realtime analytics dashboards

Polling the database every second for aggregates does not scale. Instead pre-compute metrics in batch or stream jobs, materialize summary tables, cache hot results with TTL, use read replicas for heavy readers, and push updates to browsers with WebSockets or Server-Sent Events when freshness matters. Align data freshness SLAs with cost.

Choosing a database for a chat application

Chat mixes high write volume, time-ordered reads, and presence/ephemeral state. Relational databases like PostgreSQL work for moderate scale with good indexing and partitioning. Very large systems may use Cassandra/Dynamo-style wide-column stores for inbox partitions, Redis for presence, and object storage for media. The honest interview answer names tradeoffs: consistency vs availability, query patterns, and ops skills.

Spring Security + JWT — full walkthrough

Start from a login endpoint: the client posts credentials. Spring Security’s authentication manager delegates to a UserDetailsService (or custom provider) to load the user and compare passwords using a PasswordEncoder. On success, you build a JWT with claims (subject id, roles/scopes, issued-at, expiry) and sign it with your chosen algorithm. Return the token to the client (JSON body or secure cookie policy depending on your threat model).

On subsequent requests, the client sends Authorization: Bearer <token>. A servlet filter (often custom OncePerRequestFilter) extracts the header, parses the JWT, verifies signature and expiry, and constructs an authenticated Authentication object with authorities. That object is stored in SecurityContextHolder for the request thread. Downstream, method security or the authorization filter checks roles against the secured resource. On logout or revocation, you need a server-side denylist, short expiries, or refresh-token rotation—pure JWT alone does not “invalidate” instantly without extra machinery.

OOP pillars in interview language

Encapsulation means objects guard their own state. Instead of every caller tweaking fields, you expose methods that enforce rules—non-negative amounts, required dates, valid state transitions. That localizes bugs: when something is wrong, you inspect one class, not fifty callers. Abstraction is the public story of what an object does without exposing how. Inheritance shares structure vertically; use it when the relationship is stable and truly taxonomic. Polymorphism lets you substitute implementations: Spring’s dependency injection is polymorphism plus configuration—your service depends on PaymentClient, not a concrete class.

JVM memory layout and GC collectors

Beyond heap and stack, the JVM uses Metaspace (class metadata—replaced the old PermGen), code cache for JIT-compiled native code, and optionally direct buffers outside the normal heap. Collectors include Serial (simple, pause-the-world), Parallel (throughput-oriented), G1 (common default on servers—targets pause times while collecting regions), and low-latency collectors like ZGC/Shenandoah on newer JDKs. Unless you tuned GC in production, say honestly that you rely on defaults and metrics, and you would profile before changing flags.

Young and old generations are not “marked” as labels you set in code; the JVM promotes objects based on survival through minor collections. Reachability analysis determines garbage; generations are an optimization based on observed object lifetimes.

Spring circular dependencies revisited

Constructor injection cycles fail fast because neither bean can be partially constructed. That is good: it forces a design fix. Setter injection can create half-initialized beans if you are careless. @Lazy injects a proxy that delays the real dependency until first use—sometimes legitimate, sometimes a band-aid. Long-term, extract a smaller collaborator both sides need, or invert the dependency direction.

Kafka versus RabbitMQ (conceptual)

Kafka’s core metaphor is a durable, ordered, partitioned log. Consumers track offsets; they can replay history within retention. That makes Kafka strong for event sourcing patterns, analytics pipelines, and high-volume fan-out with consumer groups. RabbitMQ’s metaphor is flexible routing from exchanges to queues with acknowledgements—excellent for task queues, RPC-style reply queues, and classic enterprise messaging. Your Docker experience with RabbitMQ positions you to explain exchanges, bindings, durability, and DLX clearly even if Kafka is only theoretical.

Gateway authentication responsibilities

The gateway is a trust boundary for the public internet. It validates credentials once, applies coarse authorization (is this token allowed to hit any route?), enforces TLS, may terminate bot traffic, and injects identity headers for internal services that sit on a private network. Internal services might still re-validate JWT signatures if they do not fully trust the network—or they might trust mTLS between mesh sidecars. The pattern depends on zero-trust maturity.

Hibernate first-, second-, and query-level cache

First-level cache is automatic per session and keeps your working set consistent within a transaction. Second-level cache shares entity data across sessions—great for read-mostly reference data if invalidation strategy matches update frequency. Query cache stores result sets of queries as a list of entity identifiers tied to timestamp regions; when entities change, stale query cache entries are dangerous. Many production apps run fine with only L1 plus good fetch planning.

Checked vs unchecked (why both exist)

Checked exceptions document recoverable contingencies in the method signature—callers must acknowledge failure modes. They became controversial because they clutter APIs and encourage empty catches. Unchecked exceptions model defects or rare systemic failures where every layer should not declare throws. Modern Spring wraps many checked JDBC exceptions into unchecked DataAccessException hierarchies for ergonomics.

TreeSet, HashSet, HashMap relationships

Conceptually, a set is a map with only keys (no separate values). Hash-based structures depend on good hash functions and equality; tree-based structures depend on ordering consistency—if compareTo violates contract (not transitive), trees break mysteriously.

Hash collisions explained slowly

A collision means two distinct keys land in the same bucket index. That is expected occasionally; the map still works by scanning the bucket and comparing with equals. Attackers can try hash collision denial-of-service on older JDKs; that is why seeding and treeification exist. In interviews, emphasize correctness (equals/hashCode) and average vs worst-case complexity.

After splitting the token, verify the algorithm header matches what you expect (prevent alg: none attacks), verify signature with the right key, validate temporal claims, and optionally enforce audience/issuer binding. Store secrets or private keys in HSM/Key Vault in real systems.

OOP pillars (comprehensive)

Encapsulation bundles data with the methods that operate on that data and hides internal representation behind a controlled API (getters/setters or richer behavior). The goal is maintainability and invariant safety: callers cannot put an object into an illegal state without going through your code.

Abstraction emphasizes what an object offers at its boundary, not how it works inside. Interfaces and abstract classes are language support for abstraction; good naming and small public surfaces are design support.

Inheritance models “is-a” specialization: a subclass inherits fields and methods from a superclass and may override behavior. It enables reuse of common structure but can couple subclasses to parent implementation if overused.

Polymorphism means “many shapes”: code written against a supertype (interface or superclass) can run against any compatible subtype at runtime. The JVM resolves instance method calls by the actual object’s class (dynamic dispatch).

Multiple inheritance — how and why in Java

Java allows a class to extend only one superclass to avoid the diamond problem (two parent classes with the same method—ambiguous inheritance). Java allows a class to implement many interfaces, which is multiple inheritance of type and abstract contracts, not multiple inheritance of stateful class implementation.

Since Java 8, interfaces can have default methods with bodies. If two interfaces provide defaults with the same signature, the implementing class must override and resolve the conflict explicitly. That is how Java gives some of the power of mixins while keeping single superclass rules.

Why this design: simpler language rules, fewer ambiguous hierarchies, clearer linearization of class initialization (constructors chain to one super).

Hashtable is a JDK1 relic: all public methods synchronized, hurting throughput under contention. Prefer HashMap with local concurrency control or ConcurrentHashMap for shared structures. Collections.synchronizedMap wraps a HashMap with a single lock—often worse than CHM for read-heavy workloads.

Multithreading, deadlock, synchronized vs ReentrantLock

Multithreading shares the heap across threads; each thread has its own stack. Races happen when two threads read/write shared mutable state without happens-before ordering (locks, volatile, atomics, concurrent utilities).

Deadlock needs four ingredients (Coffman): mutual exclusion, hold-and-wait, no preemption, circular wait. Classic example: thread 1 locks A then waits for B; thread 2 locks B then waits for A. Fix strategies: lock ordering (always acquire A before B), timeouts, try-lock (tryLock), smaller critical sections, or avoid nested locks.

synchronized is JVM-built-in monitor locking on an object or static class. It is simple and reentrant (same thread can re-enter). ReentrantLock offers explicit lock()/unlock(), optional fair ordering, tryLock with timeout, and interruptible lock acquisition—useful when you need more control than synchronized blocks.

final, finally, finalize

final (keyword): on a variable, assign-once; on a method, no override; on a class, no subclass.

finally (block): always runs after try when leaving the block (normal completion, return, or exception) except if the JVM exits abruptly. Use it to release resources; prefer try-with-resources for AutoCloseable instead of manual finally closes.

finalize (Object method): GC callback—deprecated for removal, nondeterministic, can harm GC performance. Do cleanup in try-with-resources, Cleaner (JDK 9+), or explicit lifecycle methods—not finalize.

default and static in interfaces — common misconception

A top-level interface is not “static by default” in the same sense as a nested type. The word static applies to members: fields in an interface are implicitly public static final; nested types declared inside an interface are implicitly static.

Since Java 8, interfaces may contain static methods (called on the interface name, not on instances) and default instance methods (implemented in the interface, inheritable by implementors). Those exist so interfaces can evolve without breaking every implementation. default methods are inherited and can be overridden; static interface methods are not inherited to implementing classes’ instance type in the same way—call with InterfaceName.method().

Stack: per-thread frames, locals, references. Heap: object instances, generational young (Eden/Survivor) and old; objects promoted after surviving collections. GC: reclaims unreachable objects from roots. See the main JVM section for strings and deeper detail—this block is the interview one-minute version.

@Component vs @Bean (Spring)

@Component (and @Service, @Repository, @Controller) marks your class so component-scanning picks it up and registers a bean from that class. @Bean is a method in a @Configuration class whose return value becomes a bean—ideal for third-party classes you cannot annotate, or when construction needs explicit Java logic. Both produce Spring-managed beans; the mechanism differs (classpath scanning vs explicit factory method).

N+1 problem (Spring / JPA)

You load N parent entities (one query), then accessing a lazy association on each triggers one extra query per parent → 1 + N queries. Fixes: JOIN FETCH in JPQL, entity graph, DTO projection with join, batch size tuning, or sometimes eager fetch where appropriate. Always verify with SQL logging in dev.

Spring Data JPA (what to say)

Spring Data JPA gives you JpaRepository<Entity, Id> with CRUD and paging out of the box, query methods derived from names (findByStatusAndCreatedAfter), custom @Query (JPQL/native), Specification for dynamic predicates, and integration with @Transactional on services. Hibernate is the typical JPA provider under the hood.

Programming problem — first non-repeating character

Input: "SWISSIT". Counts: S×3, W×1, I×2, T×1. Scanning the string left to right, the first character whose count is 1 is W (S fails, W succeeds).

Brute force O(n²): for each index i, scan the whole string counting occurrences of charAt(i); return first with count 1.

HashMap O(n): first pass count frequencies; second pass walk the string in order and return the first char with count 1. HashMap does not guarantee iteration order—do not iterate the map’s keySet for “first in string”; always second pass over the original string.

LinkedHashMap: can preserve insertion order of keys if you build counts by traversing the string once and putIfAbsent—still simplest interview answer is HashMap counts + linear scan of string.

ConcurrentHashMap: correct for concurrent updates from multiple threads; for one string on one thread it adds no benefit. Use it when a shared map is updated under concurrency.

// First non-repeating in O(n) time, O(k) space (k = alphabet size)
String s = "SWISSIT";
Map<Character, Integer> freq = new HashMap<>();
for (char c : s.toCharArray()) {
  freq.merge(c, 1, Integer::sum);
}
for (char c : s.toCharArray()) {
  if (freq.get(c) == 1) {
    System.out.println(c); // W
    break;
  }
}

SQL — employees with repeating dates of birth

Table Emp(id, name, dob). You want which DOBs appear more than once (and usually how many). Your draft had two issues: typo GRPOUP, and SELECT COUNT(*) ... GROUP BY dob without selecting dob loses which date the count refers to. Correct pattern:

SELECT dob, COUNT(*) AS cnt
FROM Emp
GROUP BY dob
HAVING COUNT(*) > 1;

To list all employee rows that share a DOB with someone else, use a subquery or window function (if supported):

-- Example: join back to names for only “duplicate dob” groups
SELECT e.id, e.name, e.dob
FROM Emp e
JOIN (
  SELECT dob FROM Emp GROUP BY dob HAVING COUNT(*) > 1
) d ON e.dob = d.dob;
